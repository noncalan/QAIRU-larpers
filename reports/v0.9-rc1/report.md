### Какие вопросы задать автору первыми

1. **Q-01** · P0 (блокирует разработку) · кому: архитектор: Приложение отправляет сохранение порога с amount=999: какой HTTP-код и какое тело ответа возвращает метод?
   - Варианты: A. HTTP 200, тело {"result":"ERROR","message":"Проверьте сумму"}; B. HTTP 400, тело {"message":"Некорректный запрос"}; C. HTTP 400, тело {"result":"ERROR","message":"Проверьте сумму"}
2. **Q-02** · P0 (блокирует разработку) · кому: бизнес: Уведомление выключено, расходы за месяц 55 000 ₸ при пороге 50 000 ₸, клиент включает уведомление: когда он получит push?
   - Варианты: A. Сразу после включения уведомления; B. При следующей учтённой покупке в этом месяце; C. В этом месяце push не будет, только при переходе через порог в следующем
3. **Q-03** · P0 (блокирует разработку) · кому: архитектор, бизнес: Пришёл возврат на 3 000 ₸, а исходной покупки у сервиса расходов нет (ещё не пришла или была до запуска): как учитывается возврат?
   - Варианты: A. Возврат откладывается до прихода исходной покупки; B. Возврат уменьшает расходы текущего месяца; C. Возврат не учитывается
4. **Q-04** · P0 (блокирует разработку) · кому: бизнес: Покупка на 4 000 ₸ совершена 31 января в 23:58, а проведена процессингом 1 февраля в 00:03 по Алматы: в расходы какого месяца она входит?
   - Варианты: A. Покупка входит в январь — по дате совершения; B. Покупка входит в февраль — по дате проведения
5. **Q-05** · P0 (блокирует разработку) · кому: бизнес: Порог 20 000 ₸, 10 марта push уже отправлен, 12 марта порог изменён на 50 000 ₸, 20 марта расходы дошли до 50 500 ₸: отправляется ли второй push за март?
   - Варианты: A. Нет: не больше одного push на карту в месяц при любых сменах порога; B. Да: каждая смена порога разрешает ещё один push при достижении нового порога; C. Да, но после смен порога в месяце возможен только один дополнительный push

### Q-01 · P0 · архитектор · ответ на неверную сумму
**Вопрос.** Приложение отправляет сохранение порога с amount=999: какой HTTP-код и какое тело ответа возвращает метод?

**Где в документе.**
- «Ответ в случае, если параметры запроса заполнены неверно.» (раздел «Часть B. REST API › Статусы», стр. 7)
- «{"result":"ERROR","message":"Проверьте сумму"}» (стр. 7)
- «{"message":"Некорректный запрос"}» (стр. 7)

**Почему важно.** Пример ERROR стоит под кодом 200, а 400 описан как «параметры заполнены неверно». В примере 400 нет поля result. От ответа зависят обработка в приложении, мониторинг и контрактный тест; то же правило нужно для enabled вне 0/1 и пропущенного параметра.

| Вариант | Правило | Что поменять |
|---|---|---|
| A | HTTP 200, тело {"result":"ERROR","message":"Проверьте сумму"} | Сузить описание 400 до неразборчивого запроса; сумму вне диапазона отнести к ответу 200 с ERROR |
| B | HTTP 400, тело {"message":"Некорректный запрос"} | Убрать пример ERROR из раздела 200; поле result оставить только для успеха |
| C | HTTP 400, тело {"result":"ERROR","message":"Проверьте сумму"} | Перенести пример ERROR в раздел 400; сделать поле result обязательным во всех ответах с ошибкой |
| Другое | ___ | |

**Если не ответить.** Приложение и сервис реализуют разные коды. Ошибка ввода будет показана как успех или как сбой, а мониторинг пропустит отказы.
