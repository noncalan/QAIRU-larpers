## Коротко

Нужен CLI-агент, который читает документ требований (PDF и другие форматы), режет его на отдельные требования, проверяет каждое и весь набор по ISO/IEC/IEEE 29148 и IEEE 830 и пишет отчёт на русском в файл. Сдаются репозиторий и отчёт, который сгенерировал именно этот агент.

- **Статус и срок:** это отборочное задание. Сдать до **27 ноября, 23:59** через форму из Telegram. Финал с другим заданием пройдёт 4 декабря (kick-off).
- **Критерии жюри:** архитектура, техническая реализация, точность решения задачи, измеримая бизнес-ценность. Отдельно проверят, как агент переживает битые файлы и документы без текста.
- **Главный риск:** жюри в первую очередь читает отчёт и почти наверняка сверяет его со своим списком заложенных дефектов. Баллы получит тот, кто найдёт их больше всего, не выдумает лишнего и сошлётся на точную цитату. Ниже собран наш эталон дефектов.
- **Рекомендация:** конвейер «защищённый вход → нарезка → проверка каждого → проверка набора → верификатор цитат → отчёт MD + PDF». Плюс две фишки: тест-оракул, который доказывает противоречия на сценариях, и измеренная экономия времени аналитика.
- **Модель в рантайме:** Gemini с бесплатным ключом (рекомендация организаторов). Подписки Claude Max/Pro не дают API-ключа, поэтому Claude используем для разработки, а не внутри агента.
- **Время на идею:** из-за дедлайна 27.11 советую уложиться в 4–5 часов, а не в 10. Иначе не останется времени на настройку качества по метрикам.

## Разбор ТЗ

Источник: [BCC-HUB/ai-requirements-validator-task](https://github.com/BCC-HUB/ai-requirements-validator-task) (README, `docs/requirements.md`, `.env.example`, 4 коммита). Проверяемый документ: «Уведомление о расходах по карте», часть A (бизнес-требования, Ф-1…Ф-4, НФТ, данные, критерии приёмки) и часть B (REST API сохранения порога).

| Что | Требование ТЗ |
|---|---|
| Вход | Файл требований: PDF обязательно, другие форматы желательно (минимум MD и DOCX) |
| Запуск | Одна команда: путь к файлу требований и путь к файлу отчёта |
| Обязательные шаги | Чтение документа, вызов LLM, запись отчёта; мультиагентность не обязательна |
| Модель | Любая, указать в README; бесплатного Gemini достаточно |
| Критерии проверки | ISO/IEC/IEEE 29148:2018 п. 5.2.5 (свойства отдельного требования) и 5.2.6 (свойства набора), IEEE 830-1998 п. 4.3 |
| Отчёт | Файл на русском; каждое нарушение ссылается на конкретное место документа; формат свободный, на kick-off попросили PDF (делаем MD + PDF) |
| Репозиторий | Код, файл зависимостей, README (ключ, куда положить, команда, куда ляжет отчёт), `.env.example`, никаких секретов |
| Сдача | Форма (ссылку пришлют в Telegram): ссылка на репозиторий, исходный документ и отчёт агента; отчёт также лежит в папке репозитория; ручной отчёт не принимается |
| Дедлайн | 27 ноября, 23:59 (сказано на kick-off); финал 4 декабря |

**Обязательные разделы отчёта** (чек-лист жюри, наверняка проверяют по пунктам):

1. Паспорт прогона: название документа, дата, модель, версия агента (коммит или тег). Хеш коммита брать автоматически из git.
2. Таблица нарезки: ID в отчёте, ID в документе, краткая формулировка; для ненумерованных свои ID и цитата.
3. Проверка каждого требования.
4. Проверка набора целиком.
5. Сводка: число требований, число нарушений, список критичных (непроверяемые, противоречивые, неполные).
6. Итог: можно ли начинать разработку и тестирование и что исправить первым.

**Критерии стандартов, которые агент должен покрыть:** для одного требования (29148 п. 5.2.5) это необходимость, независимость от реализации, однозначность, согласованность, полнота, единичность (singular), выполнимость, прослеживаемость, верифицируемость. Для набора (5.2.6): полнота, согласованность (нет противоречий и дублей), достижимость, ограниченность (bounded), связность с потребностями. IEEE 830 п. 4.3 добавляет ранжирование по важности и стабильности и модифицируемость. Тексты стандартов платные: в промпт кладём собственные определения, а не копию стандарта (список выше по памяти, сверить с доступным источником).

## Критическое ревью: где команды потеряют баллы

Документ написан с намеренно заложенными дефектами («текст не вычитывался»). Оценка почти наверняка идёт по доле найденных заложенных дефектов и по числу ложных срабатываний (это наша догадка, не факт из ТЗ).

### Где теряют баллы

- **Битые и пустые файлы (подтверждено на kick-off).** Агент, который падает с трейсбеком на нулевом файле, зашифрованном PDF, скане без текстового слоя или файле с неверным расширением, теряет баллы за техническую реализацию. Нужен отчёт с диагностикой: что за файл, что не так, что сделать. Для скана нужен OCR или передача PDF мультимодальной модели.
- **Нет цифр бизнес-ценности.** Это отдельный критерий жюри. Нужно замерить, сколько длится ручное ревью этого документа (человек из команды засекает время) и сколько стоит и длится прогон агента, и положить эти цифры в README.

- **Отчёт не воспроизводится.** Жюри может поднять агента по README: на kick-off сказали, что всех запускать не обязательно, но обработку битых файлов будут проверять, а это без запуска не сделать. Сломанная установка, забытая зависимость или модель по платному ключу обнуляют работу. Нужны `uv`/`pip` с зафиксированными версиями, проверка на чистой машине, опционально Docker.
- **Устаревшая модель в ****`.env.example`****.** Там `gemini-1.5-flash`, её давно вывели из API. Кто скопирует конфиг как есть, получит ошибку. Актуальное имя модели сверить в AI Studio.
- **Лимиты бесплатного тарифа.** Вызов на каждое требование по каждому критерию даст сотни запросов и упрётся в RPM/RPD. Держать прогон в 10–25 вызовах, с батчами, ретраями и кешем ответов на диск.
- **PDF на входе.** Исходник в Markdown, но ТЗ требует PDF. Таблицы (критерии приёмки, параметры API) и кириллица часто ломаются при извлечении. Сделать PDF из этого MD самим и тестировать на нём; запасной путь отдать PDF напрямую мультимодальной модели.
- **Галлюцинации и общие фразы.** ТЗ прямо запрещает замечания без привязки к тексту. Каждая находка должна нести дословную цитату, а код должен проверять, что цитата реально есть в документе.
- **Пропуск междокументных дефектов.** Самые ценные ошибки сидят на стыках: Ф-2 против критерия приёмки, часть A против части B. Агент, который смотрит на требования по одному, их не увидит.
- **Нарезка только Ф-1…Ф-4.** Требования есть также в целях, UI, sequence, НФТ, данных, интеграции, трёх критериях приёмки и всей части B без номеров. За них агент должен сам выдать ID и сохранить цитату. Ожидаемо 30–45 атомарных требований.
- **Хардкод под документ.** Других файлов организаторы не дадут, но сказали, что обработку «любого документа» тоже оценят. Промпты с упоминанием «порога» и «Ф-» на чужом документе провалятся. Протестировать на 2–3 других документах.
- **Нестабильность.** Два прогона дают разные отчёты. Нужны temperature 0, структурированный JSON-вывод по схеме, зафиксированная версия модели и стабильный порядок находок.
- **Перегиб с «дефектами на всё».** Шаблонные поля («Учебный контур», «Практикум без Jira») и нормальные формулировки нельзя помечать как критичные. Нужна шкала серьёзности и калибровка.
- **Паспорт и сдача.** Версия агента должна совпадать с коммитом в репозитории. Финальный отчёт генерировать с тега `v1.0` и сдавать с тем же тегом.

## Варианты архитектуры

Рекомендую вариант D: конвейер из B и C плюс «исполняемые требования». Он закрывает все пункты ТЗ уже к концу первого дня разработки и даёт на демо то, чего не будет у других: доказанные противоречия и измеренное качество.

| Вариант | Суть | Плюсы | Минусы | Вау на демо |
|---|---|---|---|---|
| A. Один промпт | Весь документ → один вызов → отчёт | Готово за 2 часа, 1 запрос | Нестабильно, галлюцинации, пропускает стыки | Нет; так сделает половина команд |
| B. Конвейер LLM | Разбор → нарезка → проверка каждого → проверка набора → шаблон отчёта | Структура отчёта 1:1 с ТЗ, JSON-схемы, стабильно | Само по себе не отличается | Средне |
| C. Гибрид правила + LLM | Детерминированный линтер (слова-маркеры двусмысленности, единицы измерения, HTTP-методы и коды, пустые разделы) + LLM для смысла | Дешево, объяснимо, нулевые галлюцинации в правилах | Правила легко заточить под один документ | Средне |
| D. Исполняемые требования (рекомендую) | B + C + слой «тест-оракул»: для каждого требования LLM пишет тест-кейс; не смог однозначно → «непроверяемо». Плюс прогон критериев приёмки через правила Ф-требований: расхождение = доказанное противоречие | Находки с доказательством, а не мнением; прямо бьёт в «верифицируемость» и «можно ли начинать тестирование» | +1 день работы, +5–10 вызовов LLM | Высокое: «вот сценарий, вот два разных ожидаемых результата» |
| E. Панель рецензентов | 5–6 ролей (бизнес-аналитик, QA, архитектор, ИБ/PCI, аналитик API) + судья, сливающий дубли | Широкое покрытие, красиво смотрится | Много вызовов (лимиты free tier), больше ложных срабатываний | Среднее; берём 2–3 роли как часть D |

### Рекомендуемый конвейер (D)

1. **Разбор входа.** PDF/DOCX/MD → Markdown с заголовками и таблицами (например, `pymupdf4llm` или `docling`); каждой строке присваиваем якорь (раздел, страница, строка). Запасной путь: отдать PDF модели напрямую.
2. **Нарезка.** Один вызов LLM выделяет атомарные требования из всех разделов (включая таблицы и часть B), сохраняет ID документа или даёт свой (`R-01`…), тип (функциональное, НФТ, данные, интеграция, критерий приёмки) и дословную цитату.
3. **Линтер правил.** Без LLM: слова-маркеры («быстро», «удобно», «и т.д.», «при необходимости»), смешение единиц, пустые и «—» поля, GET для изменяющих методов, объявленные и фактические коды ответа.
4. **Проверка каждого требования.** Батчи по 8–10 требований, весь документ в контексте, чек-лист 9 свойств 29148 с собственными определениями и примерами; вывод по JSON-схеме: свойство, статус, цитата, объяснение, важность, исправленная формулировка.
5. **Тест-оракул.** Для функциональных требований LLM пишет граничные тест-кейсы и отмечает, где ожидаемый результат нельзя вывести из текста. Критерии приёмки документа прогоняются через правила: ожидание таблицы ≠ вывод из Ф-требований → противоречие с доказательством (дефекты 1, 2, 26).
6. **Проверка набора.** Матрица трассировки Ф ↔ критерии приёмки ↔ API ↔ данные ↔ UI, глоссарий терминов и синонимов, попарный поиск противоречий только среди требований с общими сущностями (порог, месяц, push), чек-лист полноты (ошибки, ИБ, откат, версионность).
7. **Верификатор.** Код проверяет, что каждая цитата найдена в исходнике (нечёткое сравнение после нормализации пробелов). Находки без цитаты отбрасываются; дубли сливаются; критичные перепроверяет второй промпт-критик.
8. **Отчёт.** Jinja2-шаблон с разделами 1:1 по ТЗ → `report.md` (основной) + `report.json` + опционально HTML с подсветкой дефектов прямо в тексте документа. Паспорт заполняется автоматически (`git describe`, модель, хеш входного файла).

**Защищённый вход (добавлен после kick-off).** Перед шагом 1 агент проверяет файл: существует ли он, не пустой ли, реальный тип по сигнатуре (а не по расширению), зашифрован ли PDF, есть ли текстовый слой, похож ли текст на требования. При проблеме агент не падает, а пишет отчёт с паспортом и разделом «Диагностика»: что не так, что удалось извлечь, что сделать. Код возврата ненулевой, но файл отчёта есть всегда. Частично испорченный файл проверяется по тому, что удалось прочитать, с пометкой о потерях. То же для сбоев LLM: истёк лимит, нет ключа, невалидный JSON.

**Бизнес-ценность в цифрах (отдельный критерий жюри).** В паспорт отчёта пишем время прогона, число вызовов и токенов, стоимость. В README кладём сравнение с ручным ревью этого же документа (замер команды) и recall на нашем эталоне. Смысл для банка: дефект в требованиях дешевле всего исправить до разработки, а агент даёт первое ревью за минуты вместо часов аналитика.

**Стек:** Python 3.11+, `typer` (CLI), `google-genai` или `litellm` (смена провайдера одной переменной), `pydantic` (схемы), `jinja2`, `pytest`. Запуск: `python -m validator docs/requirements.pdf -o reports/report.md`. Провайдер по умолчанию Gemini (бесплатно, жюри повторит). shai.pro, вероятно, построена на Dify, но ТЗ этого не требует, а CLI с одной командой проще воспроизвести.

**Что увидит жюри.** Презентация на отборе не нужна, поэтому «вау» должен быть в самом отчёте и README: (1) доказанные противоречия со сценарием (покупка 31.01 в 23:58: Ф-2 даёт январь, критерий приёмки — февраль); (2) исправленная формулировка для каждого критичного дефекта; (3) раздел «Качество агента» в README: recall по критичным, доля ложных, стабильность на 5 прогонах; (4) примеры отчётов на битых файлах в `reports/robustness/`. Демо и слайды оставляем на финал 4 декабря.
