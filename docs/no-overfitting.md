# Как мы не подгоняли агента под эталон

Жюри обещало проверить «любой документ». У нас есть один документ кейса (`data/input/requirements.md`) и список заложенных в нём дефектов (`docs/gold/defects.md`). Если агент хоть как-то видел этот список, цифры на нашем документе ничего не значат. Ниже написано, как устроена изоляция и что из этого проверяется кодом, а что остаётся честным ограничением.

## Что такое эталон

- **Файл:** [`docs/gold/defects.md`](gold/defects.md), 45 дефектов нашего документа с номером, местом, критерием стандарта и важностью. Машиночитаемая версия: `evals/gold.yaml`.
- **Кто составлял:** ручной разбор документа сделал Claude (первые 33 пункта), затем второй ревьюер прошёл документ без нашего списка и добавил то, чего не хватало (запись об этом в самом файле). Люди из команды эталон не писали. Поэтому recall по нему это **оценка полноты относительно списка, который тоже составлял Claude**, а не истина. Это сказано и в каждом отчёте eval.
- **Зачем:** только для измерения. По нему считаем recall, по нему сравниваем агента с базовой линией «один промпт» (`evals/`).

## Кто эталон читает

Только пакет [`evals/`](../evals/README.md) и тесты. Агент (`src/validator/`) эталон не импортирует, не открывает и не упоминает. Модель-судья в eval видит эталон, но агент во время своего прогона нет.

Дополнительно модель агента вызывается из пустой временной папки вне репозитория, чтобы в её контекст не попали ни `CLAUDE.md`, ни `docs/gold/` (решение D-008 в [`docs/decisions.md`](decisions.md)).

## Какие тесты это проверяют

Тесты идут в CI на каждый PR.

| Тест | Что проверяет |
|---|---|
| [`tests/test_gold_isolation.py`](../tests/test_gold_isolation.py) | ни один файл `src/validator/` не импортирует `evals`; нигде в пакете нет ссылок на `docs/gold`, `gold.yaml`, `defects.md`; нет ни одной последовательности из 6 слов из описаний дефектов эталона (проверка по всему пакету: код, промпты, шаблоны, чек-листы, правила линтера) |
| [`tests/test_prompt_leak.py`](../tests/test_prompt_leak.py) | то же для самого проверяемого документа: ни одной последовательности из 6 слов документа и эталона в пакете, и ни одного слова из списка «хардкода под документ» (имена полей, сущностей и значений этого документа). Ссылки на пункты стандартов (ISO 29148, IEEE 830) перед сравнением убираются: они общие |
| оба файла, тесты «ловят подсадку» | тест сам проверяет, что подложенная фраза эталона или документа в «промпт» действительно ловится, а не молча проходит |
| [`tests/test_eval_holdout.py`](../tests/test_eval_holdout.py) | чужие документы лежат без правок (SHA-256 совпадает с записанным), ни одной последовательности из 6 слов чужого документа в пакете агента (кроме ТЗ кейса: по нему агент написан), сводная таблица результатов равна пересчёту кодом |

Что тесты **не** ловят: смысловую подгонку другими словами. Для этого правило проекта (CLAUDE.md, правила 2 и 3): правки промптов смотрятся глазами на ревью PR, а доменные знания (деньги, даты, статусы, уведомления, API, персональные данные) оформлены как универсальные чек-листы со своими триггерами, а не как правила под наш документ (`src/validator/checklists/`, шаг и цифры в #35).

## Как мы не подгоняли пороги и выбор конфигурации

- **Правило записано до прогонов.** Выбор между одним и тремя проходами поиска решал код ([`evals/checkpoint.py`](../evals/checkpoint.py)) по порогам из `docs/plan.md`, которые зафиксированы до первого замера (D-011). Мы не подбирали порог под результат.
- **Ручные поправки к судье** лежат в одном файле `evals/overrides.yaml`, с автором и причиной у каждой; сейчас он пуст.
- **Кеш вердиктов судьи в git** (`evals/cache/`): цифры воспроизводятся без повторных вызовов модели.
- **Разметка precision вслепую** (#49): находки вне эталона размечают две модели, не знающие, чьи они, с контрольными ложными находками.

## Результаты не на нашем документе

Честно: чужих документов мало, эталона дефектов у них нет, а размечали находки модели, не люди.

- **Готово:** прогоны на английском и на смешанном документе, на битых файлах, на документе с командами модели внутри (`reports/robustness/`, `tests/fixtures/robustness/`). Они показывают, что агент не падает и не привязан к языку и разметке нашего документа, но recall по ним не считается: эталона у чужих документов нет.
- **Измерено на трёх чужих документах** (issue #48, `data/holdout/`): REST API `c4` под MIT, ТЗ кейса и `finuchet`, ТЗ по ГОСТ в PDF на 18 страниц под MIT. Цитаты сверены кодом: 41 из 41, 43 из 43 и 163 из 164. Precision по слепой разметке двумя моделями, Opus 5.5 и Fable 5.2 (строгая / мягкая по согласию обоих): **52,9 % / 97,1 % на `c4`**, **15,6 % / 78,1 % на ТЗ кейса**, **22,8 % / 70,1 % на `finuchet`**. На нашем документе та же разметка дала 41,7 % / 85,4 % для отчёта-кандидата v0.9-rc2 ([`evals/results/2026-11-27-precision-rc2.md`](../evals/results/2026-11-27-precision-rc2.md)). То есть на чужом документе того же жанра и размера (требования к API) агент не стал шумнее. На документе другого жанра (условия конкурса) лишняя каждая пятая находка, а на длинном аккуратном ТЗ почти каждая третья: 38 из 127, в основном среди незначительных и среди находок линтера. Критичным находкам можно верить на всех трёх: из 26 настоящих 18, спорных 8, ложных ни одной. Вопросы агента к ТЗ кейса два судьи сравнили с 13 вопросами участников kick-off: точно совпал 1, хотя бы частично 6; вопросов про то, как делать решение, агент не задаёт. Таблица, оговорки, что холдаут показал в самом агенте и что не прогнано (`repair-webapp`): [`evals/holdout/README.md`](../evals/holdout/README.md). Чужие документы гоняем только на вехах и промпты по ним не правим, чтобы не подогнать агента и под них.
- **Что не доказано:** что recall на чужих документах такой же, как на нашем. Мы этого не утверждаем.

## Как проверить самому

```bash
uv sync
uv run pytest tests/test_gold_isolation.py tests/test_prompt_leak.py
grep -rn "gold" src/validator            # пусто
uv run python -m evals.eval --help        # единственное место, где читается эталон
```
