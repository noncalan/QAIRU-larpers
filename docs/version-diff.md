# Сравнение версий ТЗ: `validator-diff`

Банк правит ТЗ итерациями. Аналитик исправил документ по отчёту агента и хочет знать: что из найденного закрыто, что осталось и не появилось ли нового из-за правок. `validator-diff` отвечает на это по двум готовым отчётам агента (`report.json` старой и новой версии), а если переданы, то и по текстам обеих версий документа.

Сравнение **не вызывает модель**: оно детерминированное, идёт за доли секунды и без интернета. Это часть issue #59 («сравнение двух версий»); несколько кругов уточнения в этот инструмент не входят.

## Команды

```bash
# 1. Проверить обе версии документа одним и тем же кодом агента
uv run validator old/spec.md out/v1/report.md
uv run validator new/spec.md out/v2/report.md

# 2. Сравнить (тексты документов по желанию, с ними точнее)
uv run validator-diff out/v1/report.json out/v2/report.json out/diff.md --json out/diff.json \
  --old-doc old/spec.md --new-doc new/spec.md
```

То же через модуль: `uv run python -m validator.diff …`. Отдельная команда, а не подкоманда `validator`: у `validator` одна команда `validator ВХОД ВЫХОД`, подкоманда сломала бы этот вызов.

Коды возврата как у `validator`: `0` сравнение сделано, `2` ошибка аргументов, `4` отчёт или документ не прочитать (пустой, битый JSON, не отчёт агента, нет обязательного поля). Сообщения по-русски, без трассировки. Разница между версиями код возврата не меняет: «пускать дальше или нет» решает CI по `diff.json` (пример: [`ci/gitlab-ci.example.yml`](../ci/gitlab-ci.example.yml)).

## Как сопоставляются требования

По очереди, каждый следующий способ только для того, что не сопоставил предыдущий:

1. **`stable_key`**: хеш нормализованной цитаты требования. Совпал, значит текст не менялся, даже если номер `R-NN` сдвинулся.
2. **Номер и раздел документа**. Сравнение соединяет требования по паре `(source_id, section_path)`, если она уникальна в обеих версиях. Один и тот же номер может встречаться в нескольких разделах.
3. **Части одного пункта документа**: если пункт (общий номер и раздел) агент разрезал на несколько требований, они сопоставляются между собой по похожести текста с мягкой границей `SAME_SOURCE_SIMILARITY` = 30 %. Пункт тот же, поэтому переписанная фраза это правка, а не новое требование.
4. **Похожесть текста** (rapidfuzz `ratio` по нормализованному тексту) не ниже `REQ_SIMILARITY` = 70 %. Пары выбираются жадно, от самых похожих.

Итог по каждому требованию: «без изменений», «изменено», «удалено», «добавлено». Нормализация общая с агентом (`validator.text.normalize`): регистр, ё/е, кавычки, тире, пробелы, разметка Markdown и переносы строк не считаются правкой.

## Как сопоставляются находки

Первый круг строгий: пара должна пройти три проверки.

1. У находок совпадают свойство стандарта и область проверки.
2. Для находок требования есть общее сопоставленное требование. Для находок набора совпадает раздел. Если он не задан явно, инструмент использует раздел связанных требований, когда он определяется однозначно. Находки уровня всего документа сравниваются между собой.
3. Хотя бы одна пара нормализованных цитат перекрывается. Подходит вхождение одной цитаты в другую, а для длинных фрагментов также сходство `partial_ratio` от 90 %.

При нескольких кандидатах приоритет получает совпадение типа дефекта, затем порядок находок в отчётах. Каждая находка участвует максимум в одной паре. ID `F-NN` служит ссылкой внутри своего отчёта. При сравнении копий одного анализа с тем же хешем документа сохраняются и находки, у которых агент не указал требование.

Второй круг только для находок, которые остались без пары. Он нужен, чтобы один и тот же оставшийся дефект не попал сразу в «исправлено» и в «новое на изменённом месте». Область проверки у пары должна совпадать, и выполняется одно из двух:

- **Требование правили, находка осталась.** Свойство то же, требование то же, и оно имеет статус «изменено». Общей цитаты здесь быть не может: старая цитата стоит на прежнем тексте, новая на исправленном. В строке отчёта написано «требование изменено, но находка не закрыта».
- **Та же цитата и важность, другое свойство.** Модель относит один дефект то к «согласованности», то к «полноте набора». В строке написано, какое свойство на какое сменилось. Важность обязана совпасть, чтобы новая критичная находка не спряталась за старой мелкой на том же месте.

На демо без второго круга «исправлено» было бы 8 из 50 вместо 5: три находки, у которых в новой версии есть двойник, считались бы исправленными.

## Классы находок

| Класс | Когда | Засчитывается |
|---|---|---|
| **исправлено** | находки нет в новой версии, и место её цитаты изменено или удалено | да, в «исправлено N из M» |
| **пропала без правки** | находки нет, но её цитата дословно осталась в новой версии | нет: это нестабильность модели |
| **осталось** | та же находка есть в обеих версиях; если требование правили, а находка не ушла, отчёт так и пишет | — |
| **новое на изменённом месте** | новой находки не было, и её цитата взята из исправленного текста | да: возможная регрессия от правки |
| **новое на неизменённом месте** | новой находки не было, но место не менялось | нет: это нестабильность модели |

Если данных для этих классов недостаточно, находка попадает в отдельный раздел «Изменение места не подтверждено» (`unverified_place` в JSON). Такие случаи требуют сверки с документами. Они учитываются отдельно от исправлений, регрессий и подтверждённой нестабильности.

### Почему «пропала без правки» не считается исправлением

Агент вызывает модель, а модель между прогонами находит не ровно одно и то же: на одном и том же документе часть находок то есть, то нет. Если считать исправленным всё, чего нет в новом отчёте, сравнение припишет аналитику работу, которой он не делал, и цифра «исправлено» будет красивой, но ложной. Поэтому исчезновение засчитывается только там, где документ действительно правили. Симметрично новая находка на нетронутом месте не регрессия, а то, что модель в прошлый раз не отметила.

Если совпадают хеши документов, расхождение в нарезке или находках само по себе не даёт исправлений и регрессий. Для разных версий инструмент ищет цитату после нормализации. Если старая цитата исчезла из полного текста или новая появилась, у находки есть свидетельство правки. Совпадение в обоих текстах учитывается и тогда, когда аналитик переписал соседнюю фразу.

## Тексты документов или только отчёты

Пара параметров `--old-doc` и `--new-doc` включает поиск в полном тексте MD, PDF или DOCX. Без документов доступны только фрагменты из нарезки. В этом режиме подтверждением правки служит изменение цитаты в паре сопоставленных требований. Отсутствие фрагмента в нарезке может означать, что агент пропустил его в этом прогоне. Если данных для решения недостаточно, сравнение указывает это в отчёте и оставляет число исправлений прежним. В демо и CI передаются оба документа.

## Предупреждения в отчёте

- **Разные версии агента или промптов** в паспортах: часть разницы от агента, а не от правок. Для честного сравнения обе версии документа проверяют одним кодом.
- **Разные модели или настройки прогона** (профиль, число проходов).
- **Одинаковый хеш документа**: документ не менялся, вся разница от модели (так можно измерить шум модели).
- **Тексты документов не переданы.**
- **Проверка выполнена не полностью** в одном из отчётов.

## Что в отчёте сравнения

На первой странице указаны решение о начале разработки, оба светофора, число исправлений и возможных регрессий. Для решения учитываются все критичные находки новой версии. Далее идут паспорта, сводка, находки с ID обеих версий и цитатами, разбор нестабильности и таблица всех требований. В JSON поле `summary.new_critical` учитывает каждую новую критичную находку, в том числе на неизменённом месте.

Пример GitLab CI берёт документ и его сохранённый `report.json` из одного коммита целевой ветки. Путь к отчёту задаётся в `QAIRU_BASELINE_REPORT`. Задание проверяет хеш перед вызовом API, сохраняет оба отчёта и сравнение артефактами и завершается ошибкой при красном светофоре или новой критичной находке. Задайте `ANTHROPIC_API_KEY` как маскированную переменную GitLab для доверенного конвейера. [Синтаксис GitLab CI](https://docs.gitlab.com/ci/yaml/)

## Ограничения

- **Перенесённый текст.** Если правка убрала противоречие, но обе процитированные фразы остались дословно (например, фрагмент перенесли в другой раздел), находка попадёт в «пропала без правки», а не в «исправлено». Сравнение не знает смысла правки, только где менялся текст. Ошибка в сторону осторожности: исправление недосчитывается, а не приписывается.
- **Сильно переписанное требование** без номера и с похожестью ниже 70 % попадёт в строки «удалено» и «добавлено». Статус находок отдельно проверяется по цитатам.
- **Две находки одного свойства на одном месте** сопоставляются по лучшему совпадению цитат; при равенстве по порядку номеров.
- **Нестабильность модели не устраняется**, а только отделяется. Чтобы её уменьшить, обе версии проверяют с несколькими проходами (`--passes 3`), цена растёт.
- Сравнение доверяет отчётам: если агент пропустил дефект в обеих версиях, сравнение его не увидит.

## Где код

`src/validator/diff/`: `load.py` (чтение `report.json` только по нужным полям, незнакомые поля не мешают), `match.py` (сопоставление и классы), `render.py` (Markdown и JSON), `cli.py` (точка входа). Тесты: `tests/test_diff.py`. Демо для финала: [`examples/diff-demo/`](../examples/diff-demo/README.md).
