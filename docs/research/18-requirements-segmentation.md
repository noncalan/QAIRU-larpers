# 18. Нарезка документа на атомарные требования

Дата: 25.11.2026. Исполнитель: Claude (субагент researcher). Модель агента по D-006 — Claude API, ключа пока нет (D-007), поэтому вызовы LLM здесь не запускались, всё измеренное получено кодом.
Стенд: `experiments/18-segmentation/` (препроцессинг, эталон нарезки, метрики, проверка якорей в PDF/DOCX).

Пометки: **[пров.]** запускал сам на наших файлах; **[док]** официальная документация; **[статья]** прочитан абстракт или текст статьи; **[не проверено]** не удалось проверить.

Подвопросы:
1. Что известно о выделении требований из текста: «требование или нет», свободное извлечение LLM, разбиение составных, таблицы, API, критерии приёмки, схемы в тексте? Какие цифры?
2. Сколько и каких требований в нашем документе? Эталонная нарезка для eval.
3. Что делает код до LLM и что остаётся модели?
4. Схема `Requirement` и правила ID.
5. Как мерить качество нарезки с эталоном и без него?
6. Что сломается на «любом документе»: длинный, без нумерации, не документ требований, PDF с таблицами?

## TL;DR

1. **Свободное извлечение моделью теряет требования и добавляет лишние.** Gemini 3.1 Pro с 2-shot нашла 43 из 71 эталонных требований (recall 60,6 %) и добавила правила «из общих знаний» (Tagliaferro et al., 04.2026). В ReqFusion у одиночной модели 34 % ложных извлечений, а при согласии двух провайдеров 8 % (03.2026). Отсюда принцип **«LLM указывает, код цитирует»**. Код режет документ на блоки и предложения с ID. Модель помечает каждый блок и режет его на атомы ссылками на ID. Текст цитаты копирует код. Так цитаты валидны по построению, а пропущенный блок сразу виден.
2. **Наш документ: 82 содержательных блока, 29 из них (35 %) не требования.** Эталон для eval: 43 обязательные единицы и 55 атомов, ещё 8 необязательных. Номер из документа есть у 4 единиц (Ф-1…Ф-4), это 10 атомов из 55. Остальным 45 агент присваивает свои ID. 30 атомов из 55 лежат в части B, 14 в строках таблиц. Ловушка: в 10 из 14 строк чек-листа ревью есть слово «требование» (6 строк с него начинаются), но требованиями к продукту они не являются **[пров.]**.
3. **Базовые линии без LLM** **[пров.]**. Нарезка «только нумерованные пункты» покрывает 4 из 43 единиц (0,09). Нарезка «каждое предложение и строка таблицы» покрывает все 55 атомов, но 31 из 102 элементов не требования (точность 0,70). Значит, на этом документе модель нужна не чтобы найти требования, а чтобы отсеять лишнее, типизировать и связать части. Цель: recall ≥ 0,95 при точности «это требование» ≥ 0,9.
4. **PDF ломает якоря, особенно в таблицах** **[пров.]**. Цитаты эталона находятся в тексте PDF так:
   - PyMuPDF `get_text()` по умолчанию: точно 19 из 79 (цифры, стрелки и ₸ уезжают из строки);
   - pdfplumber: 69;
   - `get_text(sort=True)` с одной правкой нормализации: 65 точно и 5 нечётко.

   Девять строк многоколоночных таблиц целиком не находит ни один экстрактор. Спасает сверка по ячейкам `find_tables()` без пробелов и знаков: 53 из 64 ячеек.
5. **Схема и ID.** Номер в отчёте `R-NN` идёт по порядку документа, атомы получают `R-NN.k`. Исходный ID (`Ф-2`) сохраняется дословно. Где номера нет, пишем локатор: «Query-параметры: amount», «Критерии приёмки, строка 2», «Логика работы метода, п. 4». ID не зависят от формулировок модели, поэтому стабильны между прогонами.
6. **Метрики готовы и проверены.** `seg_eval.py` считает:
   - валидность цитат;
   - recall по единицам;
   - P/R/F1 по атомам при IoU ≥ 0,5 и мягкий recall;
   - склейки и выделенные «не требования».

   На синтетическом плохом ответе скрипт поймал все 5 подложенных ошибок **[пров.]**. Без эталона в рантайме отчёт показывает: покрытие блоков (цель 100 %), полный список исключённых блоков с причинами и дыры в нумерации. Страж по модальным глаголам на нашем документе слаб: сигнал есть лишь в 20 из 45 блоков с требованиями **[пров.]**.
7. **Цена: один вызов на наш документ**, около 8k токенов на вход и 6k на выход **[не проверено: токены оценены, ключа нет]**. По ценам на 25.11.2026: Opus 5.5 около $0,15, Sonnet 5.5 около $0,08, Haiku 5.5 меньше $0,01, без учёта thinking **[док]**. Документ с разметкой блоков становится кешируемым префиксом и общей «системой координат» для всех следующих шагов. Работа: 10–15 часов.
8. **Встроенные цитаты Claude (Citations) несовместимы со строгим JSON в одном вызове** (ошибка 400) **[док]**. Для нарезки берём structured outputs и ID блоков, ID проверяет код. Citations с документом из пользовательских блоков (блок = чанк) остаются вариантом для шага находок.

### 1.2. Атомизация: что считать «единичным» требованием

- По 29148:2018 п. 5.2.5 Singular: одно требование содержит одно обязательство. Несколько условий допустимы, несколько обязательств нет. По INCOSE GtWR это R18 «одна мысль» и R19 «без связок между независимыми обязательствами». У EARS ноль или больше предусловий, ноль или один триггер, одна система и одна или больше реакций. Источник: `docs/research/01-standards-criteria.md`.
- Ivanov et al. размечают по предложению, а список склеивают в одно требование, если элементы не полные предложения [статья]. Это совпадает с нашим правилом: перечисление полей одного объекта остаётся одним требованием с `atomic_parts`.
- Вывод: в рантайме атом по умолчанию равен предложению, и эту границу ставит код (`razdel`). Модель режет предложение дальше только при двух независимых обязательствах и только подстрокой исходного текста. На нашем документе все 55 атомов эталона совпали с границами предложений, строк таблиц и блоков кода **[пров.]**.

### 1.3. Таблицы, API, критерии приёмки, схемы в тексте (практика, литературы мало)

| Источник требований | Как резать | Кто делает |
|---|---|---|
| Таблица «поле | значение» (паспорт, общие параметры API) | Строка = кандидат. Сериализация «Ключ: значение». Метаданные (автор, проект Gitlab) или требование (метод, авторизация, URL)? Решает модель по смыслу, не по форме таблицы | код + LLM |
| Многоколоночная таблица параметров или полей ответа | Строка = одно требование, колонки = атрибуты: `Parameter: amount; Format: integer; …`. Заголовок повторяется в каждой строке, поэтому строка понятна без соседей | код |
| Критерии приёмки «Исходные условия / Действие / Ожидаемый результат» | Строка = одно требование типа `acceptance`. Колонки по синонимам заголовков раскладываются в given/when/then (дано, предусловие → given; действие, когда → when; ожидаемый результат, тогда → then). Для Gherkin в тексте то же по ключевым словам. Эти поля нужны шагу «сценарий-свидетель» (03) | код |
| Коды статусов и примеры тел ответа | Описание кода и пример тела — разные блоки. Модель связывает их полем `links`, но не склеивает | LLM |
| Нумерованные шаги («Логика работы метода») | Пункт = требование, локатор «п. N» | код |
| Схемы стрелками в тексте (BPMN, sequence) | Предложение = одно взаимодействие или поток. Дробить по стрелкам можно, мягкая метрика этого не штрафует | код + LLM |
| OpenAPI/Swagger, YAML/JSON во входе | Операция, параметр и ответ = кандидаты, разбор детерминированный | код **[не проверено: в нашем документе нет]** |
| Схема картинкой в PDF | Текста нет. Диагностика «схема на стр. N не разобрана» или PDF-вход Claude (страница уходит в модель картинкой) | код + LLM **[не проверено]** |

### 2.4. Спорные решения разметки (их стоит проверить человеку)

- **Ф-4, второе предложение** («Если она ниже…») — отдельный атом, хотя без первого предложения непонятно, к чему относится «она». В схеме для этого есть поле `depends_on`.
- **Перечисления одного объекта** не дробятся: шесть полей в «Требованиях к данным», четыре элемента экрана, «Проверить сумму и переключатель». Если агент разрежет их по «и», мягкий recall (`atom_covered`) это примет, а строгий P/R покажет как гранулярность.
- **Пример тела ответа** считается доп. цитатой требования к коду статуса, а не отдельным требованием. Исключение: `{"result":"ERROR",…}` под 200 (G46). Это отдельное утверждение «при ошибке возвращается 200».
- **Архитектура и схема B** необязательны: это описание компонентов, а не поведение. BPMN и Sequence обязательны, потому что описывают поведение и обмен данными.
- **Чек-лист ревью** не требование к продукту. Это шаблон проверки документа. Идея-кандидат заполняет его отдельным механизмом, и в нарезку он не идёт.

### 2.7. Сколько вызовов и как не потерять таблицы

- **Вызовов: 1** на документ такого размера (82 блока, до 64 атомов на выходе). Второй вызов нужен, только если в ответе не хватает блоков (повтор по списку пропущенных). Делить на два вызова по частям A и B стоит, только если eval покажет потери в хвосте документа (3.6).
- **Чтобы не потерять требования из таблиц:**
  - код разбивает таблицу на строки и даёт каждой свой ID блока;
  - заголовок таблицы повторяется в сериализации каждой строки;
  - модель обязана вернуть решение по **каждому** ID блока, полноту проверяет код;
  - строки параметров и полей ответа по умолчанию считаются требованиями, если модель не объяснила обратное;
  - в PDF таблицы берутся из `find_tables()`, а не из потока текста.

## 3. Схема данных и алгоритм

### 3.1. Что делает код, что модель

| Шаг | Код | LLM |
|---|---|---|
| Разбор входа в блоки | Заголовки → путь раздела. Абзацы, пункты, строки таблиц, блоки кода → ID `B001…`. Предложения → `B023.1…` (`razdel`). Строки, страницы, адрес ячейки | — |
| Метки документа | Regex меток (`Ф-1`, `REQ-12`, `FR.3`, `ТР-2.1`) в начале блока. Порядковые номера пунктов. Дыры и дубли нумерации | — |
| Подсказки | Флаги: пустая строка таблицы, ячейки вида «Да / Нет» (шаблон), блок кода (пример), обязательства («должен», «необходимо», «не допускается», инфинитив в начале пункта, числа с единицами, HTTP-методы и коды). Только подсказки, ничего не выбрасывается | — |
| Классификация блоков | — | Каждый блок: `requirement` / `context` / `metadata` / `template` / `example` / `placeholder`, с короткой причиной |
| Атомизация | По умолчанию атом = предложение или строка таблицы | Разрезать предложение, только если в нём два и больше независимых обязательств, `sub_span` = дословная подстрока. Связи `links` и `depends_on` |
| Тип, сущности, краткая формулировка | Given/when/then из заголовков таблицы | `type`/`subtype`, `entities` (суммы, периоды, события, системы, эндпоинты, статусы, поля данных), `summary` до 15 слов |
| Цитата и якорь | **Копирует текст** по ID и проверяет `sub_span ⊂ предложения`. Строка, страница, ячейка | Никогда не пишет цитату сама |
| ID отчёта | `R-NN`, `R-NN.k` по порядку документа | — |
| Проверки | Каждый блок получил решение, нет атома без ссылки, нет дублей. Список исключённых блоков с причинами | — |

### 3.2. Как блоки выглядят для модели (иллюстрация формата, не текст промпта)

```text
[B023] §Часть A › Требования к изменениям › Функциональные требования | пункт списка | строка 38 | метка: Ф-2
  [B023.1] Месяц определяется по дате совершения покупки в Алматы.
  [B023.2] В расходы входят проведённые покупки.
  [B023.3] Возврат уменьшает расходы месяца исходной покупки.
  [B023.4] Переводы и снятие наличных исключаются.
[B090] §Часть B › Параметры запроса › Query-параметры | строка таблицы 2 | строка 143
  Parameter: amount; Format: integer; Size: 32 bit; Mandatory: Да; Logic: 1 000–1 000 000; Description: Порог в тенге; DB field: limit_kzt
```

Этот рендеринг документа кладётся первым блоком во **все** вызовы агента как кешируемый префикс. Шаги проверки и набора ссылаются на те же `B…`, и код переводит их в цитаты. Минимальная длина кешируемого префикса у текущих моделей 512 токенов, наш документ заведомо больше [док].

### 3.3. Схема `Requirement` (проект, утвердим на сессии идеи)

```python
class Anchor(BaseModel):
    block_ids: list[str]               # ["B023"]
    sentence_ids: list[str]            # ["B023.2"]; для строк таблиц пусто
    line_start: int | None             # MD/TXT/DOCX→MD
    line_end: int | None
    page: int | None                   # PDF, с 1
    table_cell: str | None             # "таблица 3, строка 2, колонка Logic" (PDF и DOCX)
    char_start: int                    # смещения в исходном тексте после извлечения
    char_end: int
    extraction: Literal["text", "table", "ocr", "repaired"]   # для пометок в отчёте (04)

class Requirement(BaseModel):
    id: str                            # "R-07" или "R-07.2"; ставит код по порядку документа
    parent_id: str | None              # "R-07" у атома
    source_id: str | None              # "Ф-2" дословно; None, если номера нет
    source_locator: str                # "Ф-2, предл. 2/4" | "Логика работы метода, п. 4" | "Критерии приёмки, строка 2"
    section_path: list[str]
    type: Literal["goal", "ui", "process", "functional", "interaction", "nfr", "data",
                  "integration", "acceptance", "api", "constraint", "other"]
    subtype: str | None                # для api: method|auth|url|param|body|response|status|logic|rule
    quote: str                         # текст из документа, копирует код
    summary: str                       # краткая формулировка (пишет LLM), до 15 слов
    anchor: Anchor
    atomic_parts: list[str] = []       # подстроки quote у перечислений одного объекта
    given_when_then: dict | None       # для acceptance: {"given": ..., "when": ..., "then": ...}
    entities: dict[str, list[str]]     # amounts, periods, events, actors, systems, endpoints, statuses, data_fields
    links: list[str] = []              # связанные блоки (пример тела ↔ код статуса)
    depends_on: str | None             # атом, без которого этот непонятен («она» → предыдущий)
    decided_by: Literal["code", "llm"]
    stable_key: str                    # sha1(нормализованная цитата)[:10]: сравнение прогонов и версий документа
```

Ответ модели (structured outputs) короче, чем `Requirement`. В нём нет цитат и якорей, только ссылки:

```json
{"blocks": [{"block": "B069", "label": "metadata", "reason": "служебное поле: проект Gitlab"}],
 "requirements": [{"refs": ["B023.1"], "sub_span": null, "type": "functional", "subtype": null,
                   "source_id": "Ф-2", "summary": "...", "entities": {"periods": ["месяц"]},
                   "links": [], "depends_on": null}]}
```

### 3.4. Правила ID

1. **Отчётный ID** `R-NN` выдаётся по порядку первого якоря в документе (две цифры, после 99 три). Атомы одной единицы получают `R-NN.k`. Единица без разбиения остаётся `R-NN`.
2. **Исходный ID** сохраняется дословно, без перенумерации и нормализации: `Ф-1`, не `F-1`. У атомов добавляется позиция: «Ф-2, предл. 3/4».
3. **Нет номера:** вместо ID пишется локатор «раздел, п. N», «таблица: ключ строки» или «раздел, абзац N» и сохраняется цитата. Именно так требует ТЗ («агент присваивает свои и сохраняет цитату»).
4. **Дубли и дыры в исходной нумерации** (два `Ф-3`, нет `Ф-5` между `Ф-4` и `Ф-6`) идут в проверку набора (IEEE 830 п. 4.3.8, прослеживаемость), а не исправляются молча.
5. **Стабильность:** ID зависят только от порядка блоков и решений «требование / нет», а не от формулировок модели. `stable_key` по цитате позволяет сравнивать версии документа и кешировать проверки.
6. **Семантические дубли не схлопываются при нарезке.** Пример: правило из части A и такое же правило в части B. Обе цитаты остаются, повтор ловит проверка набора (модифицируемость, согласованность).

Как это выглядит в таблице отчёта (иллюстрация):

| ID в отчёте | ID в документе | Краткая формулировка | Тип | Где |
|---|---|---|---|---|
| R-06.1 | Ф-1, предл. 1/2 | Держатель активной карты KZT задаёт порог 1 000–1 000 000 ₸ | functional | стр. 2, строка 37 |
| R-15 | — (Критерии приёмки, строка 2) | Покупка 31.01 23:58, проведена 01.02 00:03, учитывается в феврале | acceptance | стр. 3, таблица критериев, строка 2 |
| R-36 | — (Query-параметры: amount) | `amount`: integer, обязательный, 1 000–1 000 000 | api/param | стр. 6, таблица Query-параметров, строка `amount` |

### 3.5. Длинные документы, документы без нумерации, не-требования

- **Чанкинг по структуре, а не по символам.** Блоки атомарны, поэтому режем по границам разделов верхнего уровня, без перекрытия. В каждый вызов передаём оглавление (все заголовки) и общий глоссарий. Порог на один вызов задаём **объёмом вывода**, а не длиной входа: ориентир до 100 атомов, около 7–8k выходных токенов. Входной контекст у текущих моделей 1M, выход до 128k [док], но ExtractBench и Lost in the Middle говорят против одного огромного ответа. Число 100 надо подобрать на eval **[не проверено]**.
- **Без заголовков:** окна по 120 блоков с перекрытием 5 блоков, дубли убираются по ID блока.
- **Без нумерации:** работает так же, только `source_id` пустой у всех. Отчёт явно пишет: «в документе нет идентификаторов, агент присвоил R-01…R-NN, у каждого цитата».
- **Не документ требований** (письмо, протокол, счёт):
  - меньше 3 требований или меньше 5 % блоков с требованиями → диагностика IN-081 из темы 04 («похоже, это не документ требований») и отчёт с паспортом и нулём требований, без выдуманных находок;
  - пороги подобрать на 2–3 чужих документах **[не проверено]**.
- **Требования в виде вопросов** (RFI) и неявные обязательства в юридических пунктах: главные источники пропусков у Ivanov и ReqFusion [статья]. Сигналы обязательства их не ловят. Пусть их ловит модель по смыслу, а в отчёте будет оговорка.

### 3.6. Режимы без ключа и replay (D-007)

- **Без ключа:** нарезка «каждое предложение и строка таблицы» кодом (recall атомов 1,0, точность 0,70 на нашем документе), пометка в паспорте «нарезка без модели».
- **Replay:** ответ вызова нарезки пишется в лог и переигрывается. ID блоков детерминированы, поэтому записанный ответ применим, пока не изменились документ и препроцессинг. Хеш входа и версия `preseg` идут в ключ кеша.

## 4. Проверка качества

### 4.1. С эталоном (eval, `seg_eval.py`)

| Метрика | Как считается | Цель |
|---|---|---|
| `quote_valid` | Доля цитат, найденных в документе (точно, затем rapidfuzz ≥ 90). При «LLM указывает, код цитирует» должна быть 1,0 по построению | **1,0** |
| `unit_recall` | Единицы эталона (req), с которыми пересекается хотя бы одна цитата | ≥ 0,95 (≥ 41 из 43) |
| `atom_recall` / `atom_precision` / F1 | Сопоставление один-к-одному при IoU спанов ≥ 0,5 (аналог partial-схемы SemEval-2013 9.1). Необязательные не идут ни в числитель, ни в знаменатель | recall ≥ 0,9, precision ≥ 0,85 |
| `atom_covered` | Атом покрыт объединением цитат не меньше чем на 80 %. Не штрафует за мелкую нарезку | ≥ 53 из 55 |
| `is_req_precision` | 1 − (элементы вне любых цитат эталона) / все элементы | ≥ 0,9 (базовая линия 0,70) |
| `merged_items`, `split_atoms` | Склейки (элемент покрывает ≥ 2 атомов) и разрезы | для диагностики |
| `req_line_cover` | Строки с требованиями эталона, покрытые цитатами | ≥ 0,95 |
| `missed_units` | Список пропущенных gid | пусто |

Проверка самой метрики **[пров.]** на синтетическом ответе `sample_pred_bad.json` с пятью типичными ошибками LLM:
1. перефраз вместо цитаты;
2. выдуманное требование;
3. потерян хвост документа (коды 400–500);
4. Ф-2 не разрезан;
5. в нарезку попали две строки чек-листа ревью.

Результат: `quote_valid 0,96`, `unit_recall 37/43` (в пропущенных G01 из-за перефраза и G47–G51), `merged_items 1`, `false_items 2`. Все пять ошибок видны.

### 4.2. Без эталона (в рантайме и в отчёте, раздел «Качество нарезки»)

- **Покрытие блоков:** решение получили N из N содержательных блоков. Цель 100 %. Пропущенные идут в повторный вызов, затем в список «не классифицировано».
- **Валидность цитат:** 100 %. Проверяется кодом, хотя цитаты и так копирует код.
- **Список «Не вошло в нарезку»:** все блоки с меткой «не требование» выводятся в приложение с причиной от модели. Для длинных документов они группируются по причине и показываются счётчиком. Страж по сигналам обязательства проверен на эталоне и оказался слабым **[пров., `guard_signals.py`]**. Модальные глаголы, инфинитив-команда, число с единицей, HTTP-метод или код и стрелка нашлись только в 20 из 45 блоков с требованиями (44 %): документ пишет описательно («Месяц определяется…», «Возврат уменьшает…»). Это согласуется с 61–65 % у Abualhaija et al. Среди 29 блоков без требований сигнал сработал в 7, и все 7 ложные: «Не требуется» в строках чек-листа совпало с «требуется». Поэтому опора — полный список исключённого с причинами, а сигналы годятся только для сортировки этого списка (сигнальные блоки сверху).
- **Нумерация:** сколько исходных ID найдено, есть ли дыры и дубли, какая доля требований без ID (у нас 82 % атомов).
- **Распределение по типам и разделам:** раздел с требованиями по заголовку («Нефункциональные требования»), но без единого требования, — сигнал для проверки полноты.
- **Стабильность** (опционально, ×2–3 вызова): Jaccard множеств `stable_key` между прогонами. Блоки, по которым прогоны разошлись, помечаются «спорная нарезка».

## 5. Рекомендации для нашего агента

1. **Взять схему «LLM указывает, код цитирует».** Препроцессинг `preseg.py` довести до модуля, модель возвращает только ссылки на `B…`. Это закрывает правило 4 CLAUDE.md на шаге нарезки без отдельного верификатора.
2. **Один вызов нарезки** на документ до ~100 атомов, structured outputs, ответ по каждому блоку. Повтор только для пропущенных блоков. Для длинных документов чанки по разделам.
3. **Таблицы — строки с сериализацией «Колонка: значение».** Критерии приёмки раскладываются в given/when/then кодом. Для PDF таблицы берутся из `find_tables()` с якорем на ячейку.
4. **В PDF-ветке темы 04 поменять порядок:** для якорей `pdfplumber.extract_text()` или `get_text(sort=True)`, а не `get_text()` по умолчанию. В `quote_check.normalize` добавить удаление пробела перед знаком препинания.
5. **Эталон нарезки** (`gold_segmentation.yaml`) перенести в `evals/` вместе с `gold.yaml` после проверки человеком. Метрики `seg_eval.py` включить в общий eval: нарезка меряется отдельно от дефектов, как и предлагала тема 08.
6. **Режим без ключа:** нарезка по предложениям кодом с пометкой в паспорте.

Оценка стоимости:

| Что | Часы | Вызовы LLM на прогон |
|---|---|---|
| Препроцессинг MD/DOCX в модуль (на базе `preseg.py`), тесты | 2–3 | 0 |
| PDF: текст с порядком, таблицы `find_tables()`, якорь «стр./таблица/строка/ячейка», сверка без пробелов | 3–4 | 0 |
| Вызов нарезки: схема ответа, промпт с общими правилами атомизации, сборка `Requirement`, ID, повтор для пропущенных блоков | 3–4 | 1 (+1 при пропусках) |

| **Итого** | **10–15** | **1–2** |

Токены и деньги на наш документ (оценка): вход около 8k (документ 3,5–5k, разметка блоков около 2k, инструкция и схема около 2k), выход около 6k (82 решения по блокам и около 60 атомов). Цены [док, 25.11.2026]:

## 6. Риски и что не удалось проверить

- **Качество нарезки моделью не измерено.** Ключа нет (D-007). Первый живой замер: прогнать промпт нарезки и посчитать `seg_eval.py`. До ключа можно через `claude -p` в пустой папке, как в базовой линии темы 11.
- **Эталон нарезки разметил один разметчик.** У ReqFusion согласие людей на идентификации κ 0,78 [статья]. Нужен второй взгляд и метка `optional` для спорного. Эталон не должен попасть в промпт (правило 2).
- **Подгонка.** Правила атомизации и подсказки в коде общие: метки вида «буквы-цифры», синонимы given/when/then, модальные глаголы. Ни одного раздела или термина нашего документа. Проверять на 2–3 чужих документах.
- **Structured outputs и большой `enum` ID блоков** — не проверено. Выбран `pattern` и проверка кодом. Время компиляции грамматики на первой схеме не мерили.
- **Citations и строгий JSON несовместимы** [док]. Если команда захочет встроенные цитаты на шаге находок, ответ там придётся разбирать из текста.
- **PDF:** 11 из 64 ячеек таблиц не сопоставились даже без пробелов (PyMuPDF режет ячейки посреди слова). На PDF из Word или браузера с другой вёрсткой **не проверено**. PDF-вход Claude (текст и картинка страницы, 1 500–3 000 текстовых токенов и до 1 568 визуальных на страницу [док]) может читать таблицы лучше, но цитаты модели придётся сверять с нашим извлечением нечётко.
- **Оценка токенов не проверена.** По документации 1M токенов ≈ 2,5M символов [док]. Для русского текста отношение, скорее всего, хуже, отсюда диапазон 3,5–5k на наш документ.
- **Расхождения с D-006** (сверить и поправить в журнале):
  - чтение из кеша у Opus 5.5 и Sonnet 5.5 стоит 0,05 базовой цены входа (у Haiku 5.5 0,1), а не «около 0,1»;
  - лимит запроса с PDF на Claude API сейчас 128 МБ, а не 32 МБ; страниц 600, или 100 при контексте меньше 1M [док, 25.11.2026].
- **Цифры статей.** ReqFusion не описывает правило сопоставления с эталоном. DLR-статья мерит синтетические документы. ReqGenX не публикует P/R. Lost in the Middle не перечитывал. Площадка ReqGenX (ESEM 2026) и DLR (IEEE Aerospace, по DOI) установлены по результатам поиска.
