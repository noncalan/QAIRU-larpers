## Главное за минуту

1. **Критериев два набора, закрывать нужно оба.** На сайте хакатона: «Уточнение» (агент задаёт нужные уточняющие вопросы по ТЗ), «Архитектура», «Ценность», «Презентация и защита», по 25 %. В эфире назвали: архитектура, техреализация, точность, измеримая бизнес-ценность. Следствие: в отчёте обязателен раздел **«Вопросы к автору ТЗ»**, иначе рискуем четвертью баллов (07).
2. **Для отбора сдаются «демонстрация работы агента и репозиторий»** (FAQ сайта). Нужна запись терминала на 30–60 секунд в начале README (07).
3. **Один промпт находит меньше половины дефектов.** Бенчмарк 10 моделей 2026 года: recall лучших 33–47 % при 11–26 % ложных тревог, новые модели не лучше старых (02). Голый LLM нашёл 0 % противоречий на реальных данных, гибрид «правила/логика + LLM» нашёл 60 % при точности 94 % (02, 03). Значит, выигрывает не модель, а конвейер вокруг неё.
4. **Главные дефекты документа (№1, 2, 34 эталона) видны только при проигрывании сценария:** покупка у полуночи, смена порога после push, задержка проведения. Принцип «нет свидетеля — нет противоречия»: противоречие засчитываем, только если есть конкретная ситуация, где два требования дают разный результат. Прототип на Z3 и сценариях уже работает (03).
5. **Бесплатный Gemini сильно урезан.** Pro-моделей на бесплатном тарифе нет, у `gemini-3.8-flash` около 20 запросов в день, у `gemini-3.5-flash-lite` около 500 (по замерам третьих сторон, сверить в AI Studio). Лимит считается на проект и сбрасывается в 13:00 по Астане. Весь прогон должен укладываться в **12–15 вызовов на Flash-Lite**, с кешем ответов на диск (05, 08).
6. **`temperature 0` для Gemini 3 не годится:** Google советует оставлять 1.0, ниже модель может зацикливаться. Воспроизводимость обеспечиваем кешем, режимом replay (отчёт пересобирается из лога вызовов), паспортом прогона и голосованием 2 из 3 там, где это важно (02, 08).
7. **Битые файлы: проверка входа до парсинга.** Сигнатура, размер, шифрование, текстовый слой, доля букв (шрифты без Unicode дают мусор даже при наличии текста), размер распакованного DOCX (zip-бомба съела 2 ГБ у python-docx). Обрезанный PDF не открывает ни одна библиотека, но приём «дописать trailer» восстановил 8 из 8 страниц. Генератор 39 битых файлов и прототип проверки уже есть в `experiments/04-parsing-lab/` (04).
8. **Цитаты проверяет код, а не модель.** Нормализация текста с картой смещений, точный поиск, затем нечёткий (rapidfuzz ≥ 90). В отчёт идёт текст из исходника. Прототип на нашем документе отсекает перефраз и выдумку (03).
9. **Бизнес-ценность доказываем своим замером,** а не цифрами вроде «IBM 1:6:15:100» и «в 100 раз дороже»: у них нет первоисточника, и лид QA может это знать (07). Формула: минуты ручного ревью минус (время разбора отчёта + прогон), умноженные на ставку аналитика (≈2 470–4 640 ₸ в час по hh.kz и опросу Kolesa), плюс «что агент нашёл, а человек пропустил».

## Что реально работает (с доказательствами)

| Приём | Эффект | Цена | Источник |
|---|---|---|---|
| Весь документ в контексте каждого вызова | −42 % ложных срабатываний, precision 0,57 → 0,75 | 0 вызовов | 02 (Poulsen et al., 2026) |
| Сценарий-свидетель для противоречий | LLM без опоры: точность 1,4 %; со свидетелем 38,5 % | 2–3 вызова | 03 (VeriSpec, 2026) |
| Гибрид правил и LLM для противоречий | 0 % → 60 % recall при precision 94 % | 1–2 вызова | 02 (Gärtner & Göhlich, 2024) |
| Детерминированные правила (REST, единицы, пустые поля, слабые слова) | 89 % precision и recall на требованиях финансовой отрасли (английский) | 0 вызовов | 02 (Paska, TSE 2024) |
| Голосование 2 из 3 | Небольшой прирост согласия с экспертами; единогласие прогонов можно показывать как уверенность | ×3 на выбранный шаг | 02 (Ronanki et al., 2023) |
| Вердикт «неясно» и список «НЕ является нарушением» в рубрике | Снижает ложные тревоги на «однозначности» и «соответствии шаблону», где их больше всего | 0 | 01, 02 |
| Доменный чек-лист с триггерами | Пункт включается, только если в документе есть его сущность (сумма, период, push, HTTP-метод) | 1–2 вызова | 09 |

Чего ждать не стоит: русских словарей слабых слов на нашем документе почти нечего ловить (0 расплывчатых слов, полезных срабатываний 6–8), правила покрывают 12–16 из 45 дефектов, и в основном средние и низкие (01). Линтер нужен как дешёвый объяснимый слой, но выигрыш не в нём.

## Что увидит жюри: самые выгодные элементы

Ранжирование из темы 07 (эффект на лида QA / часы работы):

1. «Вопросы к автору ТЗ» с привязкой к цитате, вариантами ответа и флагом «блокирует разработку» (5 / 1,5–2 ч).
2. Карточка находки: цитата, якорь, свойство и пункт стандарта, важность, «почему это проблема для разработки и тестирования», предложенная формулировка с плейсхолдерами вместо выдуманных правил (5 / ядро).
3. Итог-светофор «Разработка: нельзя / Тестирование: нельзя» и топ-5 «исправить первым» (5 / 1 ч).
4. Противоречия, доказанные сценарием (5 / 6–10 ч).
5. Раздел «Качество агента»: recall по критичным, precision, стабильность, 100 % валидных цитат, метод разметки (5 / 4–6 ч).
6. Заполненный чек-лист «Ревью требований» из шаблона банка, если он есть во входе (4–5 / 2–3 ч).
7. Битые файлы: 6–8 случаев с отчётами-диагностиками и таблицей в README (4–5 / 3–4 ч).
8. Матрица покрытия критериев стандартов (каждый пункт 5.2.5, 5.2.6, 5.2.7, 830 4.3.x: проверен ли, сколько нарушений) (4 / 1–2 ч).

Как «вода» прочитаются: веб-UI, «рой из 10 агентов» без метрик, экспорт в Jira, GitHub Action, мифические цифры ROI, 60+ стилистических придирок, английский текст в отчёте. Всё это лучше оставить на финал 4.12 или не делать.

## Готовые решения: где наше место

Коммерческие инструменты (IBM RQA, QVscribe, Jama Connect Advisor, Visure, Innoslate) проверяют язык одного требования и почти не ловят противоречия и полноту набора. IBM RQA на LLM (май 2026) устроен как наш конвейер, но своих цифр точности не публикует. Open-source классика (ARM, QuARS, Smella, Paska) работает только с английским, LLM-проекты на GitHub мелкие (до 56★), ни один не проверяет цитаты кодом и не публикует eval. Публичных решений конкурентов по кейсу пока нет (06).

Наше отличие: русский язык, проверка набора со сценариями-свидетелями, проверка API-контракта, финтех-чек-лист, вопросы автору, измеренное качество.

## Стек (рекомендация, утвердим на сессии идеи)

- Python 3.11+, `uv`, `src`-layout, команда `uv run validator ВХОД ВЫХОД`; запасные пути: `uvx --from git+…@v1.0` и `pip install -r requirements.txt` (08).
- `google-genai` + `pydantic` (structured output по JSON Schema), свой адаптер на ~150 строк: ретраи, кеш на диск, JSONL-лог вызовов, темп ≤ 12 запросов в минуту (05, 08).
- Разбор входа: PyMuPDF 2.x + запасной pypdfium2/pdfplumber за общим интерфейсом, DOCX через python-docx с проверкой размера архива, MD/TXT с определением кодировки (charset-normalizer). Проверка входа и коды возврата 0–5 по прототипу `guard.py` (04).
- Отчёт: JSON → Markdown + PDF через Typst (08).
- Eval: свой `eval.py` + `gold.yaml` (цитаты как якоря), recall/precision, стабильность, стоимость; holdout из 2–3 своих документов и мутационные тесты против подгонки (08).

## Риски и открытые вопросы

- **Лимиты Gemini не опубликованы официально.** Цифры 20/500 запросов в день взяты с форума и сторонних замеров. helknow сверит в AI Studio (тема 10).
- **Подгонка под документ.** Финтех-чек-лист (09) писался с оглядкой на эталон: покрывает 44 из 45 дефектов. Примеры «плохо/хорошо» из нашего документа в промпты не кладём, а сам чек-лист проверяем на чужих документах.
- **Ложные «доказательства».** Неверная формализация требования даёт ложное противоречие. Оракул должен показывать сценарий, обе цитаты и оба ожидаемых результата, чтобы человек мог проверить.
- **Цифры статей 2026 года** (arXiv 2608.*, 2609.*) прочитаны субагентами, но общий лимит загрузки страниц кончился на середине. Перед тем как цитировать их жюри, перепроверить `fact-checker`.
- **Регуляторика РК в 2026 году поменялась** (новый закон о банках, постановление НБРК № 48 о ИБ утратило силу). В отчёте агента ссылаемся без номеров пунктов, кроме закона о персональных данных (09).
