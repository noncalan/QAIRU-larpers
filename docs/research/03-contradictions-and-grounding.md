# 03. Противоречия, неполнота и защита от галлюцинаций

2026-11-25 · исследование для обсуждения идеи (не решение). Опирается на эталон из `case-analysis.md` (номера дефектов #1…#45 оттуда).

Прототипы, на которых проверены утверждения этого файла (иллюстрации, не код агента):
- `experiments/03-proto/quote_check.py`: верификатор цитат (rapidfuzz 3.14.6), прогнан на `docs/requirements.md`.
- `experiments/03-proto/z3_conflicts.py`: Z3-модели для #1, #2, #34 (z3-solver 5.4.1.0), все три запускаются и дают ожидаемый unsat core.

## TL;DR

1. **Главные противоречия эталона (#1, #2, #34) составные и сценарные.** Они видны только если «проиграть» ситуацию: дата у полуночи, смена порога после уже отправленного push, задержка проведения. Попарный NLI и промпт «найди противоречия» их не ловят надёжно. Литература это подтверждает: NLI проваливается на составных конфликтах (Fazelnia et al., 2024), LLM без формальной опоры даёт recall 0–32 % на противоречиях против 60–75 % у гибрида (ALICE, 2024, LLM — GPT-3), а у VeriSpec конвейер без шага LLM-верификатора даёт точность 1,4 % (3 из 221), с верификатором, который обязан предъявить ситуацию-свидетеля, — 38,5 % (5 из 13); «просто спросить LLM» дало 0 % (0 из 16) [исправлено фактчекером: 1,4 % — это базовая линия PLAINDETECT, а не прямой промпт; VeriSpec проверял OpenAI Model Spec (правила поведения LLM), а не требования к ПО; вклад именно свидетеля отдельной абляцией не измерен].
2. **Принцип «нет свидетеля — нет противоречия».** Противоречие засчитывается, только если есть конкретная ситуация, в которой два требования (по отдельности!) дают разный результат. Это идея VeriSpec (2026) и тест-оракула из нашего варианта D. Она же даёт жюри (лиду QA) доказательство, а не мнение.
3. **Рекомендуемый модуль «проверка набора»** (≈4–6 вызовов LLM): глоссарий и теги сущностей при нарезке → кластеры по общим сущностям вместо O(n²) → три детектора: (а) оракул «критерии приёмки × функциональные требования» плюс граничные сценарии; (б) таблица решений на каждую точку решения («слать push?»), где код находит конфликтные и пустые строки; (в) трассировка + CRUD + доменный чек-лист для неполноты. LLM предлагает, код проверяет: даты, суммы, единицы и полноту таблиц считает Python.
4. **Z3 стоит брать узко,** как «слой доказательства» поверх маленького JSON-DSL (интервалы, «не больше N за период» против обязанности, отнесение события к периоду), а не как генерацию произвольного Z3-кода. Прототип для #1, #2, #34 работает и занимает от 8 до 40 строк на случай, unsat core сам называет конфликтующие требования. LTL (nl2spec, NL2LTL, FRET) за 1,5 дня нереалистичен.
5. **Защита от галлюцинаций дешёвая и детерминированная:** цитата — обязательное поле; нормализация (NFKC, ё/е, кавычки, тире, nbsp, markdown, «1 000» → «1000») с картой смещений; точный поиск, затем `rapidfuzz.fuzz.partial_ratio_alignment` ≥ 90; в отчёт идёт текст, вырезанный из исходника по смещениям, а не текст модели. На нашем документе прототип нашёл точные и слегка искажённые цитаты со строками и отбросил перефраз (73) и выдумку (57).
6. **Остальной стек в рамках бюджета:** structured output Gemini (`response_json_schema` из pydantic) + валидация pydantic; один пакетный вызов критика для critical/major с поиском контрдоводов (облегчённый Chain-of-Verification); голосование (self-consistency) только для вызова проверки набора; confidence считает код, а не модель; статус «не уверен» уходит в раздел «Вопросы к аналитику».
7. **Бюджет вызовов жёсткий.** По сообщениям на форуме Google (сентябрь–октябрь 2026), бесплатный Gemini 3.8 Flash даёт 20 запросов в день, Flash-Lite 500; официальная страница цифр не показывает. Значит, весь прогон должен укладываться в 12–15 вызовов, голосование и отладку гоняем на Flash-Lite, ответы кешируем.
8. **Precision меряем отдельно от recall:** эталон из 45 дефектов + ручная разметка «лишних» находок двумя людьми (κ Коэна), доля валидных цитат (после верификатора 100 %), стабильность (Jaccard по 3 прогонам), внедрение дефектов в чужие документы и «чистый» документ для подсчёта ложных срабатываний, абляция «с верификатором и без».

## Рекомендуемый дизайн: «проверка набора» и «верификатор»

### Схема данных Finding

Псевдо-pydantic. Поля, которые модель не должна заполнять сама, помечены «код».

```text
Anchor:            # якорь в извлечённом тексте (extracted.md кладём рядом с отчётом)
  section_path: list[str]          # ["Часть A", "Функциональные требования"]  (код: стек заголовков)
  line_start, line_end: int        # 1-based                                    (код)
  char_start, char_end: int        # смещения в извлечённом тексте             (код)
  page: int | None                 # для PDF, из постраничной карты смещений    (код)
  table: {caption, row, column} | None                                           (код)

Quote:
  llm_text: str                    # что прислала модель
  text: str                        # вырезано из исходника по смещениям, до границ слов (код)
  match: exact | fuzzy | rejected  (код);  score: float (код);  anchor: Anchor (код)

Scenario:          # evidence: доказательство
  given: list[str]; when: list[str]
  data: dict                       # сырые значения: время, суммы, порог, таймзона
  expected_by: {requirement_id: {outcome: str, quote: Quote, determined: bool}}
  checker: code | z3 | llm         # кто вынес вердикт
  checker_output: str              # "unsat core: F3b, F4, SCN" / "Ф-2 → 1, AC-2 → 2"
  assumptions: list[str]           # доменные допущения, НЕ факты документа

Finding:
  id: str                          # код: sha1(criterion + sorted(requirement_ids) + span) → стабильный между прогонами
  scope: requirement | set
  requirement_ids: list[str]       # ID из таблицы нарезки; код сверяет, что ID существуют
  criterion: enum                  # 29148 5.2.5: necessary, implementation_free, unambiguous, consistent,
                                   #   complete, singular, feasible, traceable, verifiable;
                                   # 29148 5.2.6: set_complete, set_consistent, set_feasible,
                                   #   set_comprehensible, set_able_to_be_validated; IEEE 830 4.3: ranked, modifiable
  defect_type: enum                # contradiction, ambiguity, incompleteness, missing_requirement, unverifiable,
                                   # duplicate, design_in_requirement, terminology, units, security
  quotes: list[Quote]              # ≥1; для contradiction ≥2 из разных требований
  explanation: str                 # ≤3 предложений, по-русски
  evidence: Scenario | None        # обязателен для contradiction и для critical
  severity: critical | major | minor | info   # модель предлагает, код ограничивает правилами
  status: proven | likely | uncertain         # код
  confidence: float                # код, см. ниже
  fix: str                         # предлагаемая формулировка
  question: str | None             # вопрос аналитику, если status = uncertain
  sources: list[str]               # lint, per_req, cluster, oracle, decision_table, trace, z3 (код)
  votes: int                       # в скольких прогонах найдено (код)
```

Схему отдаём Gemini через `response_mime_type="application/json"` и `response_json_schema=Model.model_json_schema()` (так в текущей документации). Документация прямо говорит: синтаксис JSON гарантирован, смысл нет, а `minLength`, `maxLength`, `uniqueItems` и подобное API молча выбрасывает. Поэтому всё равно валидируем pydantic-ом, а невалидное перезапрашиваем один раз. Модели отдаём упрощённую схему (без полей «код»), иначе большие вложенные схемы API может отклонить.

### Модуль «проверка набора» (псевдокод)

```text
def check_set(reqs, glossary, doc):
    # 0. Вход: из вызова нарезки у каждого требования есть kind (functional / nfr / data /
    #    integration / acceptance / api / ui / goal), entities (канонические имена из глоссария),
    #    actions (push, save, reject...), quote с якорем.
    findings = []

    # 1. Детерминированные проверки по глоссарию (0 вызовов)
    findings += glossary_checks(glossary, reqs)         # синонимы, термин без определения, единицы у атрибута
    findings += trace_matrix_orphans(reqs)              # functional без acceptance, "читает" без API-метода...
    findings += crud_gaps(glossary.entities, reqs)      # сущность создаётся, но не читается / не удаляется
    findings += api_status_consistency(reqs)            # объявленные коды против кодов в примерах

    # 2. Кластеры вместо O(n^2)
    clusters = group_by_shared_entity(reqs, min_size=2, max_size=12)   # "push", "порог", "месяц расходов"
    clusters += [{ac} | traced_functionals(ac) for ac in acceptance]   # каждая строка приёмки + её Ф-требования

    # 3. Один вызов: конфликты со свидетелем по всем кластерам (VeriSpec-style)
    cand = llm("cluster_verifier", clusters, doc)       # каждый кандидат ОБЯЗАН иметь witness + 2 цитаты
    cand = [c for c in cand if c.witness and len(distinct_reqs(c.quotes)) >= 2]

    # 4. Один вызов: таблицы решений для каждого action
    tables = llm("decision_tables", actions_with_reqs)  # условия (≤5 булевых), правила с цитатами
    for t in tables:
        for row in all_combinations(t.conditions):
            acts = {r.action for r in t.rules if r.matches(row)}
            if len(acts) > 1: findings.append(conflict(row, rules))      # → #2
            if not acts and row_feasible(row): findings.append(gap(row)) # → #17, #16

    # 5. Оракул: 1–2 вызова
    scen = acceptance_rows + llm("boundary_scenarios", reqs)   # BVA на интервалах, границы периодов,
                                                                # повтор события, смена настройки между событиями,
                                                                # выключенная функция, возврат раньше покупки
    preds = llm("predict_per_requirement", scen, clusters)      # по КАЖДОМУ требованию отдельно, сырые данные;
                                                                # "не определено" — допустимый ответ
    for s in scen:
        outcomes = evaluate(preds[s])                           # арифметику, даты (zoneinfo), суммы делает код
        if disagree(outcomes): findings.append(contradiction(s, outcomes))   # → #1
        if all_undetermined(outcomes): findings.append(unverifiable(s))
    # 6. Опционально: подтвердить conflict/contradiction в Z3 через DSL-шаблоны (без exec LLM-кода)
    for f in findings if f.defect_type == contradiction: f.status = z3_confirm(f) or f.status
    return findings + cand
```

Ключевой приём в шагах 3–5: **просить у модели вывод по каждому требованию отдельно и сравнивать в коде.** Если попросить «какой будет результат по документу», модель склонна молча примирить противоречие и выбрать одну трактовку.

### Модуль «верификатор» (псевдокод)

```text
def verify(findings, doc, slicing):
    nd, offmap = normalize(doc)          # NFKC; ё→е; «»“”„→"; —–‑−→-; nbsp/thin space→пробел;
                                         # * _ ` | # > → пробел; схлопнуть пробелы; lower;
                                         # "1 000 000"→"1000000"; мягкие и строчные переносы PDF ("про-\nведённые")
    for f in findings:
        for q in f.quotes:
            m = exact_find(nd, normalize(q.llm_text))
            if not m: m = rapidfuzz.partial_ratio_alignment(nq, nd, score_cutoff=90)
            if not m or len(nq) < 15:  q.match = rejected; continue
            if occurrences(nq) > 1:   m = search_within(sections_of(f.requirement_ids))   # «Да / Нет» и т.п.
            q.text = snap_to_words(doc[offmap[m.start]:offmap[m.end]])                     # канон из исходника
            q.anchor = anchors(offmap[m.start], offmap[m.end])
            q.requirement_id = slicing.owner_of(q.anchor)                                   # перепривязать ID
        drop f if no valid quotes                                     # → счётчик в приложении отчёта
        if f.defect_type == contradiction and distinct_reqs(valid quotes) < 2: f.status = uncertain
        if f.severity == critical and not f.evidence:  f.severity = major; f.status = uncertain
        apply_severity_caps(f)                       # шаблонные/пустые поля ≤ minor и т.д.
    merged = dedup(findings)                         # ключ: семейство критерия + множество ID + пересечение
                                                     # спанов (IoU > 0.5) или token_set_ratio объяснений > 80;
                                                     # слияние: объединить цитаты и sources, max(votes)
    critic = llm("critic", [f for f in merged if f.severity in (critical, major) and f.status != proven])
                                                     # 1 вызов: для каждой находки ищет в документе текст,
                                                     # который снимает дефект; keep / downgrade / drop + причина
    for f in merged: f.confidence = score(f)         # код
    return sorted(merged, key=(severity, first_anchor))
```

### Как мерить precision (и не обмануть себя)

1. **Валидность цитат:** доля цитат, прошедших верификатор, до него и после. После должна быть 100 %. Доля «до» — хорошая цифра для README: «модель ошиблась в X % цитат, верификатор их отсёк».
2. **Recall по эталону:** находка ↔ дефект эталона, если пересекаются якоря и совпадает семейство критерия. Матчинг автоматический, подтверждение ручное. Отдельно recall по critical (#1–4, 6, 8, 14, 34, 25).
3. **Precision:** находки, не сматченные с эталоном, двое из команды независимо размечают: верная новая / ложная / дубль / мелочь. Считаем κ Коэна, расхождения разбираем. Precision = (сматченные + «верная новая») / все. Отдельно precision по critical: жюри больнее всего видеть ложное «критично».
4. **Стабильность:** средний Jaccard множеств ключей находок по 3 прогонам; доля critical, найденных 3 из 3.
5. **Обобщение (против подгонки):** 2–3 чужих документа (свои или из PURE, на который ссылаются Malik 2023 и Lubos 2024), в каждый внедряем 8–10 дефектов известных типов (пара противоречий, смешение единиц, нет метода API, критерий приёмки против правила), считаем recall. Плюс «чистый» короткий документ: любое critical на нём — ложное срабатывание. Так делает VERIMED (внедрение дефектов, 63 из 64).
6. **Абляция для раздела «Архитектура»:** базовый промпт против конвейера; конвейер без верификатора / без критика / без оракула. Одна таблица с цифрами закрывает и «архитектуру», и «точность».

Честно про цифры: на 45 дефектах доверительные интервалы широкие (±10–15 п.п.), поэтому в README даём абсолютные числа («найдено 31 из 45, ложных 4 из 39»), а не только проценты.

## Как агент мог бы ДОКАЗАТЬ #1, #2 и #34

Общий принцип для всех трёх: LLM только извлекает правила и предлагает ситуацию, проверяет код или солвер. Ни одно правило ниже не знает слов «порог» или «Ф-»: оно работает с типами «событие отнесено к периоду», «действие обязательно / запрещено / ограничено N за период», «термин из доменного чек-листа без определения».

### #1. Ф-2 против критерия приёмки 2 (отнесение события к периоду)

**Общее правило R-PERIOD.** Если требование относит событие к периоду (день, месяц) по какой-то дате, а критерий приёмки или граничный сценарий содержит событие у границы периода, оракул сравнивает период по правилу с периодом в ожидании. Граничные сценарии генерирует техника анализа граничных значений: 23:59/00:00 на стыке периодов, разные даты у «совершения» и «проведения», таймзона.

**Данные (извлекает LLM, сырые значения):**
- Ф-2: правило `bucket = month(purchase.committed_at, tz="Asia/Almaty")`, цитата «Месяц определяется по дате совершения покупки в Алматы.»
- AC-2: события `committed_at = 31.01 23:58`, `posted_at = 01.02 00:03 Asia/Almaty`; ожидание `counter[февраль] += 4000`, цитата «Февральский счётчик вырос на 4 000 ₸».

**Проверка (код):** `month(31.01 23:58, Asia/Almaty) = 1`, а ожидание = 2. Месяц считает `zoneinfo`, не модель. Допущение в `assumptions`: 23:58 тоже по Алматы (в документе таймзона указана только у второго события).

```python
bucket = Int('bucket_month')
s.assert_and_track(bucket == purchase.month, 'F2: месяц = месяц даты совершения')  # purchase из zoneinfo
s.assert_and_track(bucket == 2,               'AC2: ожидается рост февральского счётчика')
s.check()  # unsat, core = [F2, AC2]
```

Z3 здесь избыточен: хватает сравнения в Python. Он нужен только для единообразного вывода «unsat core».

**В отчёте:** «Противоречие доказано сценарием. Покупка совершена 31.01 в 23:58 и проведена 01.02 в 00:03. По Ф-2 она относится к январю, по критерию приёмки 2 — к февралю. Исправить: выбрать, какая дата определяет месяц (совершения или проведения), и привести критерий в соответствие.» Побочный эффект того же правила: граничный сценарий «январская покупка проведена в феврале, push уже был в январе» без ответа в тексте даёт неполноту #35.

Попутно: системная tzdata (2026e) даёт Asia/Almaty UTC+6 до марта 2024 и UTC+5 после, что подтверждает #36. На Windows у Python нет системной tzdata, поэтому пакет `tzdata` надо зафиксировать в зависимостях агента.

### #2. Ф-3 против Ф-4 (обязанность против ограничения частоты)

**Общее правило R-DEONTIC / таблица решений.** Для каждого действия (здесь push) собираем все требования, которые его обязывают, запрещают или ограничивают «не больше N за период». Конфликт = существует допустимая ситуация, где одно требование обязывает действие, а другое его запрещает.

**Таблица решений (LLM заполняет правила с цитатами, код перебирает строки):**

| Порог пересечён снизу | Push в месяце уже был | Порог менялся после него, накоплено < нового | Ф-3 | Ф-4 | Итог |
|---|---|---|---|---|---|
| да | нет | — | push | — | ок |
| да | да | нет | нет push | — | ок |
| да | да | да | **нет push** («максимум один такой push за календарный месяц») | **push** («следующее достижение вызывает push независимо от истории») | **конфликт** |
| нет | любое | любое | — | — | нет правила: проверить, допустимо ли (здесь допустимо) |

Если в таблицу добавить условие «уведомление включено», появятся пустые строки: что считать, пока оно выключено, и что делать при включении выше уже накопленной суммы. Это неполнота #17.

**Свидетель (предлагает LLM, проверяет Z3):** порог 20 000 ₸; 10.01 покупки на 25 000 ₸ → push №1; 15.01 порог поднят до 50 000 ₸ (25 000 < 50 000); 20.01 покупка 30 000 ₸ → итог 55 000 ₸. По Ф-4 нужен push №2, по Ф-3 он запрещён.

**Z3-модель (сокращённо, полная версия в `z3_conflicts.py`):** ограниченная трасса из 4 событий в одном месяце. Z3 сам ищет ситуацию; LLM нужен только для перевода требований в шаблоны.

```python
N = 4
spent = [Int(f's{i}') for i in range(N+1)]; thr = [Int(f't{i}') for i in range(N+1)]
push  = [Bool(f'p{i}') for i in range(N+1)]; kind = [Int(f'k{i}') for i in range(N+1)]  # 0 покупка, 1 смена порога
cross = lambda i: And(kind[i] == 0, spent[i-1] < thr[i], spent[i] >= thr[i])
no_prior = lambda i: And([Not(push[m]) for m in range(1, i)])
s.assert_and_track(DOM, 'DOM: допустимые входы (Ф-1: 1000..1000000, расходы растут, смена порога сохраняет сумму)')
s.assert_and_track(And([Implies(And(cross(i), no_prior(i)), push[i]) for i in range(1, N+1)]), 'F3a')
s.assert_and_track(Sum([If(p, 1, 0) for p in push]) <= 1, 'F3b: максимум один push за месяц')
s.assert_and_track(And([Implies(And(kind[j] == 1, spent[j] < thr[j], cross(k), first_cross_after(j, k)), push[k])
                        for j in range(1, N+1) for k in range(j+1, N+1)]), 'F4: независимо от истории')
s.assert_and_track(And([Implies(push[i], cross(i)) for i in range(1, N+1)]), 'F3c/BPMN: push только при достижении')
s.assert_and_track(Or([And(push[i], kind[j] == 1, spent[j] < thr[j], cross(k))
                       for i in range(1, N+1) for j in range(i+1, N+1) for k in range(j+1, N+1)]), 'SCN')
s.check()   # unsat; core = [DOM, F3b, F4, F3c, SCN]
```

Результат прогона: без F3b и F4 ситуация выполнима (проверка «не вакуумно», как у VERIMED); со всеми требованиями unsat, core = {DOM, F3b, F4, F3c/BPMN, SCN}. Человекочитаемый свидетель 25 000 / 50 000 / 55 000 без F3b даёт ровно 2 push, с F3b — unsat.

**Урок из прототипа (важно для дизайна).** В первой версии я перевёл первую фразу Ф-3 буквально: «переход → push» без оговорки. Тогда core показывал конфликт внутри самого Ф-3, а Ф-4 в него не попадал. Формализация зависит от прочтения, и ошибка перевода даёт ложное или неверно адресованное «доказательство». Отсюда правила: (1) формулу каждого требования печатаем в приложении отчёта рядом с цитатой; (2) прочтение двух фраз одного требования делаем согласованным; (3) Z3 только подтверждает находку детектора, а не объявляет новые.

**В отчёте:** «Противоречие доказано. Сценарий: … По Ф-4 клиент должен получить второй push, по Ф-3 второй push в месяце запрещён. Исправить: явно указать приоритет, например "Смена порога сбрасывает ограничение одного push в месяц" или "Не более одного push в месяц, в том числе после смены порога".» Тот же сценарий вскрывает #38: в «Требованиях к данным» один «признак отправки» не поддерживает сброс из Ф-4.

### #34. «Проведённые покупки» (двусмысленный доменный термин → недостижимая цель)

**Общее правило R-INTERP.** Доменный чек-лист содержит классы терминов с известными разными прочтениями: «проведённая операция» (авторизация / клиринг / проводка по счёту), «дата операции» (совершения / проведения), «время» (чья таймзона), «сумма» (валюта, единицы). Если термин из чек-листа используется без определения в глоссарии, LLM выдаёт 2–3 прочтения с параметрами. Код или солвер проверяет каждое против целей и НФТ, которые затрагивают то же событие. Двусмысленность считается существенной, если прочтения дают разный наблюдаемый результат на одном сценарии; это критерий ClarifyGPT и проверки эквивалентности формализаций в VERIMED.

**Данные:**
- Ф-2: «В расходы входят проведённые покупки.»
- Цели: «…узнать о достижении личного бюджета в момент покупки.»
- НФТ: «Сервис передаёт push на отправку в течение минуты после получения события.»
- AC-2: «совершить» (23:58) и «провести» (00:03) — разные события. Это свидетельство из самого документа, что проведение не совпадает с покупкой.
- Допущения (из доменного чек-листа, в отчёте помечаются как допущения, не факты документа): клиринг обычно занимает 1–3 дня (по памяти, не проверял); «в момент покупки» ≈ не позже 1 минуты.

```python
lag, react = Int('posting_lag_min'), Int('push_delay_min')
for name, lag_c in [('I1: проведена = авторизована', lag == 0),
                    ('I2: проведена = клиринг (1–3 дня)', And(lag >= 1440, lag <= 4320))]:
    s = Solver(); s.set(unsat_core=True)
    s.assert_and_track(lag_c, 'TERM ' + name)
    s.assert_and_track(And(react >= 0, react <= 1), 'NFR: в течение минуты после события')
    s.assert_and_track(lag + react <= 1, 'GOAL: в момент покупки (допущение: ≤ 1 мин)')
    print(name, s.check())        # I1: sat;  I2: unsat, core = [TERM I2, NFR, GOAL]
# свидетель из документа: AC-2 фиксирует lag = 5 мин → unsat уже без доменного допущения о клиринге
```

**Вердикт агента:** «двусмысленность с последствиями», status = likely (не proven), потому что опирается на допущение о том, что такое «момент». В отчёте: «Термин "проведённые" не определён. При прочтении "авторизация" цель достижима; при прочтении "клиринг" push придёт через 1–3 дня после покупки, и цель "в момент покупки" недостижима (допущение о сроках клиринга). Критерий приёмки 2 сам разводит совершение и проведение во времени. Вопрос аналитику: какое событие процессинга запускает пересчёт?»

## Риски и что не удалось проверить

**Риски дизайна**
- **Ошибка формализации выглядит как доказательство.** Показано на #2 выше. Есть и работа NeurIPS 2026 с говорящим названием «One Requirement, Many Specifications: Systematic Instability in LLM Specification Autoformalization» (читал только заголовок). Меры: Z3 только подтверждает, формулы печатаются в отчёте, DSL вместо произвольного кода, несколько формализаций и проверка эквивалентности для critical (если хватит бюджета).
- **Никакого `exec` для кода от LLM.** Модель выдаёт JSON по шаблонам, Z3-формулы строит наш код. Иначе это дыра в безопасности, которую лид QA банка заметит.
- **Подгонка под документ.** Правила R-PERIOD, R-DEONTIC и R-INTERP и доменный чек-лист сформулированы через типы, а не через слова документа. Проверять на внедрённых дефектах в чужих документах.
- **Доменные допущения как факты.** Сроки клиринга, «момент», PCI DSS — только в поле `assumptions` и со статусом не выше likely.
- **Короткие и повторяющиеся цитаты.** «Да / Нет», «—», «Учебный контур» встречаются много раз. Нужны минимальная длина (~15 символов после нормализации) и поиск в разделе требования.
- **PDF.** Смещения считаются по извлечённому тексту, не по PDF; переносы слов, колонтитулы и разорванные таблицы ломают точный поиск. Нормализация должна склеивать переносы, а постраничная карта смещений — давать номер страницы.
- **Бюджет вызовов.** Если 20 запросов в день для Flash — правда, то голосование, критик и отладка на Flash невозможны. План: Flash-Lite для отладки и голосов, кеш ответов на диск, у каждого члена команды свой ключ для разработки (проверить, не противоречит ли это условиям Google).
- **Нестабильность даже при temperature 0.** Сортировка и стабильные ID находок обязательны, иначе два прогона дадут разные отчёты.

**Не проверено**
- Лимиты бесплатного Gemini: официальная страница (`ai.google.dev/.../rate-limits` → `aistudio.google.com/docs/rate-limits`) цифр не показывает; 20 RPD для 3.8 Flash и 500 RPD для Flash-Lite взяты из ветки форума от 3.09.2026 без ответа Google. Проверить в AI Studio. Имена моделей в документации structured output: `gemini-3.8-flash`, `gemini-4-argon`.
- Репозитории `github.com/HIPREL-Group/VeriSpec` и `github.com/lreinpold/ONCON24_Requirements_Verification_by_LLM` указаны в статьях, сам я их не открыл (лимит WebFetch исчерпан, поиск их не нашёл).
