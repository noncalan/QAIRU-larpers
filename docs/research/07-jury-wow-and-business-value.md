# 07. Что впечатлит жюри и как честно посчитать бизнес-ценность

Пометки: **[проверено]** — прочитано в источнике сегодня; **[вторично]** — по пересказу или заголовку, первоисточник не открыт; **[по памяти]** — не проверено, перед использованием сверить. ## TL;DR

1. **На сайте хакатона другие критерии, чем прозвучали в эфире.** Сайт: 4 × 25% — «Уточнение: агент задаёт нужные уточняющие вопросы по ТЗ», «Архитектура», «Ценность: качество продукта в целом», «Презентация и защита» [проверено]. В эфире Коточигов, ссылаясь на сайт, назвал архитектуру, техническую реализацию, точность и измеримую бизнес-ценность (kick-off 10:49–11:18). Закрываем оба набора. Самое дешёвое и сильное следствие: в отчёте нужен раздел **«Вопросы к автору ТЗ»**. Без него мы рискуем потерять четверть баллов, если жюри идёт по критериям сайта.
2. **FAQ сайта: для отбора сдаются «демонстрация работы агента и репозиторий»** [проверено]. Значит, нужна 30–60-секундная запись терминала в README (asciinema/GIF), хотя презентация не нужна. Это примерно час работы.
3. **Цифры «IBM 1:6:15:100» и «баг в проде в 100 раз дороже» не использовать.** «IBM Systems Sciences Institute» был внутренними учебными курсами, данные не опубликованы, а источник цепочки цитирования — учебник Прессмана 1987 г. (Bossavit; The Register, 2021) [проверено]. Лид QA может это знать. Аргументы, которые выдерживают проверку: NASA/INCOSE 2004 с оговорками, Boehm & Basili 2001 с оговоркой «5:1 для небольших некритичных систем», Doolan 1992 (замеры инспекций ТЗ в Shell), PMI 2014 «47%». Стоит показать, что мы знаем и контрдовод: Menzies et al. 2016, 171 проект, «эффект отложенного дефекта» не подтвердился.
4. **Главный аргумент ценности — собственный замер, а не литература.** Формула: минуты ручного ревью минус (время разбора отчёта агента + ожидание), умноженные на ставку часа, минус стоимость прогона. Плюс полнота: «агент нашёл K дефектов, которые человек пропустил». Сырые логи замера кладём в репозиторий.
5. **Ставки для перевода в тенге** [проверено]. hh.kz, итоги 2025: медиана предлагаемой зарплаты бизнес-аналитика 415 157 ₸, системного аналитика 340 278 ₸, тестировщика 233 980 ₸. Kolesa Group (опрос 318 человек): медиана в аналитике 780 000 ₸. Получается примерно 2 470–4 640 ₸ за час аналитика. Берём консервативно, без налогов и накладных расходов.
6. **Говорим на языке банка.** В шаблоне ТЗ есть поля «Задача в JIRA», «Gitlab project», «Swagger», «Author: Школа тестирования» и чек-лист «Ревью требований» из 14 пунктов, не заполненный. Если агент заполнит этот чек-лист (Да/Нет/Не требуется со ссылками на находки), отчёт будет вписан в их процесс. Это сильный и недорогой ход, 2–3 часа.
7. **Лид QA ценит измеримость, а не красоту.** Нужны раздел «Качество агента» (recall по критичным, precision, стабильность на 5 прогонах, 100% валидных цитат, метод разметки), противоречия, доказанные сценарием, и отчёты по битым файлам. Как «вода» прочитаются веб-UI, «рой агентов» без метрик, экспорт в Jira, GitHub Action, сравнение версий ТЗ и громкие ROI. Это всё лучше отложить на финал.

**Что лид QA, скорее всего, примет за воду или перегиб**

- Мифические цифры («IBM 1:100», «56% дефектов из требований», CHAOS «треть проектов проваливается») без оговорок.
- Число документов в месяц, взятое с потолка без пометки «допущение», и ROI в миллионах.
- Замечания без цитаты; один дефект, размноженный по пяти требованиям; 60+ «низких» придирок к стилю; помеченные как критичные шаблонные поля («Учебный контур»).
- Выдуманные номера пунктов стандарта или дословные «цитаты» стандарта (тексты платные: пишем свои определения и номера пунктов).
- Метрики без метода, recall 100% на собственном эталоне без оговорки о смещении.
- Длинное вступление про ИИ в README, где команда запуска не видна на первом экране.
- Английский текст и эмодзи в отчёте.

Безопаснее любых множителей |

**Калибровка для нашего документа.** В `requirements.md` около 684 слов (`wc -w`), то есть примерно 2,5–3,5 логических страницы по 300 слов (таблицы и код дают разброс). Отсюда ожидаемый порядок ручного ревью:
- один проверяющий со скоростью меньше 2 стр/ч (Gilb): **не меньше 1,2–1,8 ч** только на проверку, без написания отчёта;
- полная Fagan-инспекция по Doolan, 2,2 чел·ч на страницу: **около 5,5–7,5 чел·ч**.

Если наш замер выйдет сильно за этот диапазон, нужно объяснить почему.

Институт был внутренней учебной программой, исходных данных нет. Позднее статьи приписывали ему данные Boehm & Papaccio 1988 (Bossavit, Morendil gist 2016; The Register 2021) [проверено] |

**Формулировка для README, которая выдержит лида QA:** «Мы не используем популярные множители вроде "в 100 раз дороже": их первоисточники не подтверждены (Bossavit, 2012–2021). Ценность считаем по собственному замеру ниже. Направление эффекта (чем раньше найден дефект требований, тем дешевле исправление) подтверждают Boehm & Basili (2001), с оговоркой о 5:1 для некритичных систем, и NASA/INCOSE (2004).»

**Довод, который сильнее множителей, — конкретный дефект из этого документа и его цена:**
- сумма покупки в тиынах против порога в тенге: при сравнении без пересчёта push срабатывает при сотой части порога, а это массовые ложные уведомления и жалобы;
- сохранение настройки через GET с `cardId` в URL: если это PAN, номер карты попадает в логи прокси и сервера, это вопрос PCI DSS;
- 200 с телом `ERROR`: мобильное приложение покажет успех при ошибке.

Каждый такой пример — одна строка «что будет в проде», её поймёт и QA, и бизнес.

### Методика нашего замера (команда проводит сама 26–27.11)

**Принцип:** человек и агент делают одну и ту же работу по одной рубрике, результат сверяется с одним эталоном, все сырые данные лежат в репозитории.

1. **Слепой документ.** Команда уже видела `requirements.md`, поэтому замер на нём завышает скорость человека. Основной замер делаем на одном из своих тестовых документов с внесёнными дефектами (P3 знает список, ревьюер его не видел). На `requirements.md` проводим дополнительный замер с пометкой «ревьюер знаком с документом» или зовём человека вне команды.
2. **Ручное ревью (базовая линия).** Ревьюер получает документ и ту же рубрику (свойства 29148/830 и шкалу важности), выдаёт таблицу «место, цитата, свойство, важность, комментарий» и итог «можно ли начинать». Время пишет в `bench/human_review.csv` с шагом 5 минут: `t_read`, `t_analyze`, `t_write`. Перерывы не считаются, жёсткого лимита времени нет, ревьюер сам решает, когда закончил. Если возможно, двое ревьюеров: это даёт разброс.
3. **Прогон агента.** 5 прогонов на зафиксированной модели (temperature 0). На каждый пишем в `bench/runs/*.json` время прогона (`t_agent`), число вызовов, токены вход/выход, ретраи и сам отчёт.
4. **Разбор отчёта человеком (`t_triage`).** Ревьюер читает отчёт агента и помечает каждую находку: верная / ложная / дубль / верная, но вне эталона. Это одновременно даёт precision. **Без `t_triage` экономия нечестная**: агент не заменяет человека, он делает первый проход.
5. **Сопоставление с эталоном.** Находка совпадает с пунктом эталона, если указывает на то же место (пересечение цитаты или тот же ID требования) и ту же суть дефекта. Свойство стандарта может отличаться: «неоднозначность» и «противоречие» часто пересекаются. Размечают двое, расхождения решают обсуждением и записывают в `bench/adjudication.md`. Верные находки вне эталона добавляем в эталон с пометкой «добавлено после прогона» и считаем отдельно.
6. **Метрики** (для 5 прогонов: медиана и min–max):
   - `Recall = найдено_из_эталона / размер_эталона`, отдельно `Recall_крит` по критичным;
   - `Precision = верные_находки / все_находки` (верные = совпавшие с эталоном + верные вне эталона);
   - ложных на страницу; доля находок с цитатой, дословно найденной в тексте (цель 100%, обеспечивает верификатор);
   - стабильность: доля находок, которые есть в ≥4 из 5 прогонов, и разброс recall;
   - то же для человека: `Recall_чел`, `Precision_чел`, и объединение «человек + агент».
7. **Формулы ценности:**
   - `ΔT (ч на документ) = T_ручн − (T_triage + T_ожид)`, где `T_ожид` — время, когда человек ждёт агента и не может работать (если прогон фоновый, то 0; честнее учитывать);
   - `C_прогон (₸) = (токены_вх × цена_вх + токены_вых × цена_вых) × курс_USD/KZT`; на бесплатном тарифе маржинально 0 ₸, но в README пишем эквивалент по платному прайсу на дату прогона;
   - `Экономия на документ (₸) = ΔT × C_час − C_прогон`;
   - `Экономия в месяц (₸) = N_док × Экономия на документ`. **N_док — допущение банка**, в README даём таблицу для N = 10 / 30 / 100 и пишем «подставьте своё»;
   - `Прирост полноты = Recall(человек ∪ агент) − Recall(человек)` и число критичных дефектов, которые нашёл только агент. Для QA это важнее тенге;
   - (не в основную цифру) сценарий «пропущенный критичный дефект дошёл до тестирования»: используем только качественно, на примерах выше, без множителей.
8. **Иллюстрация с заглушками, только чтобы проверить формулу; в README подставить реальный замер.** Пусть `T_ручн = 3,0 ч`, `T_triage = 0,5 ч`, `T_ожид = 0`. Тогда ΔT = 2,5 ч. При 2 470 ₸/ч экономия 6 175 ₸ на документ, при 4 640 ₸/ч — 11 600 ₸. При N = 30 документов в месяц выходит 75 ч и 185 000–348 000 ₸ в месяц.
9. **Ограничения пишем сами, раньше жюри:** один-два документа; ревьюеры — студенты, а не аналитики банка; эталон составила команда (смещение); бесплатный тариф Gemini может использовать данные для улучшения продуктов Google [по памяти: сверить с Gemini API Additional Terms], поэтому для реальных ТЗ банка нужен платный тариф или модель внутри контура.
