# ADR-0005: Защищённый вход, диагностика вместо падения, коды возврата

**Дата:** 2026-11-25 (записано задним числом 2026-11-26)
**Статус:** принято
**Кто решал:** команда по ТЗ и kick-off; коды по [исследованию 04](../research/04-parsing-and-broken-files.md), разделы 3–4
**Журнал:** D-006 (проверка битых файлов без ключа) в [`docs/decisions.md`](../decisions.md)

## Контекст

Жюри отдельно проверит битые файлы и документы без текста: агент обязан выдать понятную диагностику в отчёт, а не упасть ([`docs/case/case-analysis.md`](../case/case-analysis.md)). Сбоить может всё: файл (пустой, с паролем, zip-бомба, скан, обрезанный PDF), модель (нет входа, лимит, таймаут, отказ, ответ не по схеме) и сам код. Пользователь агента — QA-инженер, ему нужна причина и что делать, а не трассировка.

## Решение

- **Шаг 0** ([`ingest/guard.py`](../../src/validator/ingest/guard.py)) решает до разбора и без модели, можно ли читать файл: тип по содержимому, размер, пароль, zip-бомба по заголовкам архива, старый `.doc`, обрезанный PDF со спасением страниц. `guard` не бросает исключений.
- **Каждый шаг** обёрнут в `pipeline._step`: исключение превращается в `Diagnostic` (код, уровень, что увидели, что сделал агент, что сделать человеку, где), дальше идёт запасной путь шага. `pipeline.run` не выпускает исключений, трассировки только в `report.log`.
- **Каталог кодов** `IN`, `LLM`, `CFG`, `INT`, `OUT` в [`errors.py`](../../src/validator/errors.py), код возврата выводит `exit_code(diagnostics)`: 0 проверка выполнена, 1 внутренняя ошибка, 2 аргументы или отчёт не записать, 3 вход прочитан частично, 4 вход не обработать, 5 сбой модели. Найденные дефекты код возврата не меняют.
- **Отчёт пишется всегда**, когда доступна папка отчёта: при сбое шаблона аварийный Markdown, при сбое PDF остаётся Markdown.

## Альтернативы

### Исключения наружу и код 1 на любую ошибку

- **Плюсы:** проще писать.
- **Минусы:** жюри увидит трассировку; нельзя отличить битый файл от нашего бага и от лимита модели.
- **Почему нет:** прямо противоречит критерию жюри.

### Проверять файл только парсером

- **Плюсы:** меньше кода.
- **Минусы:** парсер на битом файле падает чем угодно или съедает память (zip-бомба).
- **Почему нет:** нужен ответ до разбора и без модели.

## Последствия

### Хорошее

- 20 битых файлов и сбоев модели дают отчёт с причиной и кодом: [`reports/robustness/`](../../reports/robustness/README.md), тесты `tests/test_guard.py`, `tests/test_robustness.py`, `tests/test_e2e_exit_codes.py`.
- Код возврата пригоден для CI: банк может встроить агента в конвейер и различать «плохой документ» и «нет модели».

### Плохое

- Запасные пути надо поддерживать и тестировать отдельно (нарезка без модели, вопросы кодом без редактора).
- Частичный результат легко принять за полный: поэтому статус отчёта «частично» и светофор не бывает зелёным, если шаг упал или вопросы не собраны.

### Риски

- Новый вид битого файла, которого нет в каталоге: он попадёт в `IN-099` «документ повреждён» с общей подсказкой, а не в трассировку.
