## D-012 · 26.11 · Отчёт на сдачу делаем профилем `standard`, а не `submit`

Решение интегратора (поток плана) 26.11 при подготовке кандидата `v0.9-rc1` (#54). **Статус:** принято для RC1 и релиза v1.0; профиль меняется одним флагом, если Нурдаулет решит иначе.

- **Что решили.** Отчёт на сдачу (`reports/v0.9-rc1/`, затем v1.0) делаем профилем `standard`: 1 проход поиска Opus 5.5 `medium`. Профиль `submit` (1 проход `xhigh`) остаётся опцией CLI, код профилей не меняется. MD и DOCX для таблицы согласия форматов тоже идут на `standard`, лимит `--max-budget-usd 5` у каждого прогона.
- **Почему.**
  1. `xhigh` полноты не добавил. Замер 26.11 на `requirements.md` до правки промпта поиска (версия `86ee834`, с чек-листами): `submit` нашёл 84,4 % эталона (строго 71,1 %, 1 прогон) против 86,7 % (строго 73,3 %, 2 прогона) у `medium`. Разница в один дефект эталона, то есть в пределах разброса между прогонами. Критичные 100 % у обоих. Источники: [`evals/results/2026-11-26-recall-xhigh-base.md`](../evals/results/2026-11-26-recall-xhigh-base.md), [`evals/results/2026-11-26-checklists-on.md`](../evals/results/2026-11-26-checklists-on.md).
  2. `xhigh` дороже и дольше. Проход поиска на `xhigh` стоил $1,11 и шёл 431 с (50 тыс. токенов ответа) против $0,66–0,69 и 233–245 с на `medium`: в 1,6 раза дороже и в 1,8 раза дольше (`run/calls.jsonl` тех же прогонов, таблица в [`2026-11-26-recall-one-pass.md`](../evals/results/2026-11-26-recall-one-pass.md)).
  3. Финальная версия промпта поиска (v3, PR #111) замерена только на `medium`: 97,8 % в обоих прогонах. Связку v3 и `xhigh` не мерили, а сдавать немеренную комбинацию значит нарушить правило «метрики вместо „на глаз“» (CLAUDE.md, правило 5).
- **Что меняет.** D-010 в части «`xhigh` для отчёта, который сдаём, и для финала» и строку `docs/plan.md` «27.11, 07:00–09:00: прогон профилем `submit`». В README строка про `--profile` теперь говорит, что `submit` это опция.
- **Альтернатива, которую не взяли:** 2–3 прогона v3 на `xhigh` и решение по цифре. Это около $3,5 и 15 минут на прогон и лимит подписки, который нужен RC1, eval (#51) и precision (#49). Можно вернуться к этому к финалу 4.12, если появится запас лимита.

## D-011 · 26.11 · Один проход поиска по умолчанию, разметка блоков остаётся

Прогоны 25–26.11 на `data/input/requirements.md`, Opus 5.5 `medium`, судья Opus 5.5 `high` вслепую. Таблица и заметки о прогонах: [`evals/results/2026-11-26-checkpoint.md`](../evals/results/2026-11-26-checkpoint.md). **Статус:** принято по записанному правилу, Нурдаулет подтвердил 26.11 (один проход, три по флагу `--passes 3`).

- **П. 1. Проходов по умолчанию: один** (профили `standard` и `submit`), `--passes 3` остаётся опцией. Прирост у C по Жаккару есть (+0,115 при пороге +0,10), но не выполнено обязательное условие «доля сверенных цитат у C не ниже, чем у B»: 335 из 337 (99,4 %) против 194 из 194. Recall всего +3,7 п. п. при пороге 5, критичные одинаковы (100 %).
- **П. 2. Разметка блоков остаётся:** с ID блоков recall выше, чем без них (88,9 % против 85,6 %), так что поиск по-прежнему видит документ с ID блоков. Флаг `--search-input raw` оставлен для замеров.
- **П. 3. Промпт поиска до слоя доказательств не дорабатываем:** B ниже базовой линии на 4,4 п. п. при пороге 5. Строгий recall ниже на 12,5 п. п.: судья чаще ставит «частично», как и на замере #14. Зато цитаты у агента сверены на 100 % против 84,7 % у одного промпта.
- **Особое мнение (Claude), решение не меняет.** Условие по цитатам записано без допуска: когда у B 100 %, оно требует от C безошибочности, а цитат у C почти вдвое больше, поэтому исход решили две цитаты. Обе не выдуманы моделью: это показ таблицы в разметке блоков («Колонка: значение; …» и метка пустой ячейки «(пусто)»), верификатор их отбросил, итоговые находки C сверены на 100 %. По сути три прохода дают +0,115 стабильности и +8,1 п. п. строгого recall почти за то же время (проходы идут параллельно) и примерно за 1,9× цены. Если Нурдаулет решит мерить условие по цитатам с допуском, это изменение правила: записать здесь, что правило изменено и почему, и поменять `PROFILES` в `src/validator/config.py`.
- **Найдено по пути.** Лимит подписки («You've hit your 5-hour limit») при коде 429 считался перегрузкой (`LLM-004` с повтором): исправлено в PR #91, теперь `LLM-002` без повтора. Модель иногда цитирует строку таблицы так, как её показывает разметка блоков; такие цитаты верификатор отбрасывает, и это кандидат на доработку сверки цитат по ячейкам.

## D-010 · 25.11 · Какая модель и какой effort на каждом шаге агента

Решение по замеру `docs/research/21-model-and-effort.md` (33 ответа четырёх моделей на нашем документе, оценка отдельным судьёй по эталону). Номер D-009 занят итогом сессии идеи.

- **Три прохода поиска: Opus 5.5 (`claude-opus-5-5`), ответ свободным текстом, без `--json-schema`.** Effort `medium` в обычном режиме (проход ≈$0,28 и ≈2 мин; объединение трёх проходов 100 % эталона, строго 95,6 %). Effort `xhigh` для отчёта, который сдаём, и для финала (проход ≈$0,80 и до 7,5 мин; объединение 100 %, строго 100 %, стабильнее). Режим выбирается флагом CLI.
- **Каждый проход переносит в JSON Haiku 5.5 (`claude-haiku-5-5`, `medium`)** со схемой и цитатой, взятой дословно из документа. На замере ни одна находка не потерялась, 100 % цитат дословно, $0,026 за проход. Верификатор цитат кодом остаётся.
- **Остальные шаги** (не замерялись, выбор по смыслу): нарезка Sonnet 5.5 `medium`; критик, пример-свидетель и вопросы автору Opus 5.5 `high` с рассуждением текстом перед JSON; тест-кейсы Sonnet 5.5 `high`; слияние и отчёт кодом.
- **Fable 5.2 не используем:** на нашем документе не лучше Opus, вдвое дороже по API, на Pro только за кредиты, на Max до половины недельного лимита. **Haiku на поиск не ставим:** строгий recall 47–67 % против 83–90 % у Opus.
- **Почему не строгий JSON сразу:** со схемой модель думает в 3–5 раз меньше и находит меньше (Opus `medium`: 73 % против 93 % текстом). Через API со строгим JSON это не проверено, сверим в теме 19.
- **Как вызываем:** полные имена моделей, а не алиасы (`opus` переедет на новую модель); `--effort` и `output_config.effort` всегда явно (умолчания у моделей разные); `CLAUDE_EFFORT` убираем из окружения `claude -p`.
- **К условию D-009 о трёх проходах:** на замере один проход Opus `medium` находит 92,6 % (строго 83 %), три прохода вместе 100 % (строго 95,6 %), 39 из 45 дефектов найдены во всех трёх. Три прохода на `medium` стоят как один на `xhigh` (≈$0,83 против ≈$0,80). Перенос в JSON добавляет 3 дешёвых вызова Haiku к 5–8 вызовам из D-009.
- **Цена:** по D-009 ключ не пополняем, финальный отчёт и eval идут через подписку, поэтому для нас цена = расход лимитов. Цена по API нужна для README (жюри со своим ключом) и для расчёта бизнес-ценности: полный прогон ≈$1,6 на `medium` и ≈$3,2 на `xhigh` (часть шагов оценена). 94–97 % цены прохода составляет вывод, поэтому экономят effort, Haiku на переносе, replay и Batch API для eval, а не кеширование документа.

## D-009 · 25.11 · Идея агента: «Ревью с доказательствами»

Решение сессии идеи 25.11 (Нурдаулет). Полное описание, конвейер, приоритеты и риски: [`docs/ideas/final-idea.md`](ideas/final-idea.md).

- **Суть:** CLI-агент выдаёт не мнения, а проверяемые находки: дословная цитата, которую сверил код, пункт стандарта, «свидетель» (правило, пример-сценарий или пустое место в черновике теста) и следующий шаг (формулировка или вопрос автору ТЗ). Принцип: модель предлагает, код проверяет.
- **Почему так:** замер базовой линии (исследование 11, helknow): один простой промпт к Opus 5.5 уже находит около 87 % дефектов эталона, но только 71,8 % его цитат дословно есть в документе, число находок гуляет от 39 до 54, вопросов автору нет. Выигрыш агента в доверии к находкам и в вопросах автору, а не в полноте.
- **Поиск (решение Нурдаулета):** независимые проходы по всему документу с полной рубрикой и слияние кодом со счётчиком «найдено в N из 3», дальше слой доказательств (пример-свидетель, критик, верификатор цитат), вопросы автору и отчёт; 5–8 вызовов на прогон. Код поддерживает N проходов, минимум к 26.11 14:00 собираем с одним, три включаем, только если eval покажет прирост по сверенным цитатам и стабильности (три прохода в 5–6 раз дороже).
- **Вау-фичи (решение Нурдаулета):** цикл уточнения (`questions.yaml` → `answers.yaml` → `--answers`, для демо `--ask`) и попытка теста, которая показывает, какого значения не хватает. После минимума.
- **Не делаем:** «гениальный ход» (поиск стал товаром, усиливаем уточнение, безупречное обязательное и презентацию), дообучение своей модели (нет данных, эталон только для eval, малая модель слабее и ломает запуск «одной командой»), рой агентов, веб-интерфейс.
- **На доработку к финалу 4.12** (защищаем этот же агент): формальное доказательство противоречий (Z3), полный режим уточнений, сравнение версий ТЗ, дорожная карта с локальной моделью для закрытого контура банка.
- **Метрики для README и презентации:** доля сверенных цитат, стабильность между прогонами, число вопросов автору, время и цена; recall по эталону только с оговоркой, что эталон тоже составлял Claude.
- **Ключ API к сдаче не пополняем (решение Нурдаулета).** Финальный отчёт и eval идут через подписку `claude -p`. Клиент через SDK `anthropic` всё равно пишем (жюри может запустить со своим ключом), с теми же промптами и схемами, и проверяем тестами на записанных ответах; в README пишем, что вживую с ключом его не запускали. Меняет срок «ключ к 26.11» из D-007 и «к сдаче подключаем API» из D-008; D-006 (модель Claude, SDK `anthropic`) остаётся.
- **Первая страница отчёта (решение Нурдаулета):** светофор «можно ли начинать разработку и тестирование», 5 главных исправлений и 5 вопросов автору, блокирующих работу.
- **Главная номинация финала (решение Нурдаулета):** Best Architecture. Лишние часы идут в надёжность и прозрачность архитектуры, бизнес-ценность вторым планом.
- **Роли:** команда распределяет сама. Черновик Claude в `final-idea.md`, раздел «Кто что делает»; условие: ручной замер ревью делает тот, кто не видел эталона.

## D-008 · 25.11 · До 27.11 модель вызываем через подписку Claude

Решение Нурдаулета (25.11): пока на ключе нет средств, агент вызывает Claude **через подписку**, командой `claude -p` (режим Claude Code без диалога). Ключ API подключаем в конце, к сдаче.

Что из этого следует:

- **Один интерфейс клиента модели, три реализации:** `claude -p` по подписке (разработка), SDK `anthropic` по ключу (сдача и жюри), replay на записанных ответах (без сети). Остальной код не знает, какая из них работает.
- **Как вызывать `claude -p`:** из пустой временной папки вне репозитория (чтобы в контекст не попали `CLAUDE.md` и эталон), без инструментов (`--tools ""`), со своим системным промптом (`--system-prompt`), с `--output-format json` и схемой ответа через `--json-schema`. Флаги сверены по `claude --help` версии 2.1.332. Что из этого реально работает на подписке и на Windows, проверяет helknow (issue #2).
- **Лимиты подписки общие** с обычной работой в Claude Code. Оценку по эталону гоняем экономно, ответы кешируем на диск.
- **Путь через ключ пишем сразу** и проверяем в первый же час, когда ключ появится: жюри не сможет запустить агента через нашу подписку. В README для жюри: где взять ключ и как пересобрать отчёт из записанных ответов без него.
- **Паспорт отчёта** указывает модель и способ вызова (подписка через Claude Code или API).

На ключе Claude API пока нет средств (сообщение Нурдаулета, 25.11). Решение D-006 не меняется, меняется порядок работы:

- **Исследование и эксперименты без модели** (парсеры, битые файлы, линтер, сверка цитат, отчёт, оценка по эталону) идут как шли, ключ им не нужен.
- **Базовая линия «один промпт»** (тема 11) делается через подписку Claude: команда `claude -p` в пустой папке, чтобы в контекст не попали `CLAUDE.md` и эталон. Ответы сохраняем в `experiments/out/`.

- **Вызов модели через подписку** (`claude -p` из кода агента) на время разработки: решено, см. D-008.

## D-006 · 25.11 · Модель агента: Claude API

Решение Нурдаулета (25.11): агент вызывает модель через **Claude API**, официальный Python SDK `anthropic`, ключ `ANTHROPIC_API_KEY` в `.env`. Провайдера и модель больше не исследуем. Модель по умолчанию в `.env.example`: `claude-opus-5-5`, окончательно зафиксируем в плане. Отменяет исходное допущение «бесплатный Gemini» (разбор кейса, исследование 05).

Что из этого следует:

- **Устарело:** лимиты бесплатного Gemini, `google-genai`, «не больше 12 запросов в минуту», запасные бесплатные провайдеры. Файл `docs/research/05-llm-apis.md` и куски про Gemini в 00, 04, 08 помечены как устаревшие, тема 10 у helknow отменена.
- **Вызовы платные.** Кеш ответов на диск и пересборка отчёта из лога (replay) нужны теперь ради денег, а не ради лимитов. Документ требований повторяется в каждом вызове, поэтому включаем кеширование префикса (prompt caching): чтение из кеша стоит 0,05 обычной цены входа у Opus 5.5 и Sonnet 5.5 и 0,1 у Haiku 5.5 ([цены](https://platform.claude.com/docs/en/about-claude/pricing), сверено 25.11.2026 в исследовании 18).
- **Стабильность.** Текущие модели Claude не принимают `temperature` и другие параметры сэмплинга (по справке SDK на 03.11.2026), так что вывод прежний: кеш, replay и голосование по нескольким прогонам.
- **Жюри может не иметь ключа Claude.** Проверка битых файлов (шаг «защищённый вход») обязана работать без ключа, а отчёт по основному документу должен пересобираться из приложенного лога вызовов. В README агента пишем, где взять ключ и как запустить replay без него.
- **Сканы.** Claude принимает PDF напрямую (до 600 страниц; лимит размера запроса по [документации](https://platform.claude.com/docs/en/build-with-claude/pdf-support) на 25.11.2026 равен 128 МБ, в справке SDK от 03.11.2026 было 32 МБ, перед использованием сверить). Это запасной путь для страниц без текстового слоя вместо «OCR через Gemini».
- **К обсуждению идеи:** у Claude API есть встроенные цитаты (Citations: модель возвращает точный фрагмент документа и его позицию). Они ложатся на правило 4 «каждая находка с цитатой», но несовместимы со строгим JSON-выводом в одном вызове ([документация](https://platform.claude.com/docs/en/build-with-claude/citations), по справке SDK на 03.11.2026, сами не проверяли). Свой верификатор цитат остаётся в любом случае.

## D-005 · 25.11 · Порядок работы: исследование → идея → план

Сначала около часа исследования (`docs/research/`), затем 1–2 часа на выбор идеи вместе, затем общий план и issues.
