# Полнота одного прохода: правка промпта поиска

26.11.2026, Астана. Задача от Нурдаулета: поднять полноту одного прохода (recall по эталону) хотя бы до уровня одного промпта (базовая линия A, 93,3 %), честно и без подгонки под эталон. Протокол как на контрольной точке #37: агент, 1 проход Opus 5.5 `medium`, вход `data/input/requirements.md`, судья исследования 21 (Opus 5.5 `high`, вслепую), precision разметкой двумя моделями вслепую (#49).

## Что поменяли

Два добавления в `src/validator/prompts/search_system.md`, остальное как было.

1. **Новый шаг 7 «Сверь представления одного поведения между собой»** (общий приём тест-дизайна, без слов документа):
   - схема процесса (BPMN, блок-схема, диаграмма состояний или последовательности): у каждого условия из текста есть ветка, у каждой развилки описаны все исходы, порядок шагов и участники совпадают с текстом;
   - модель данных: в ней есть, где хранить всё, что читают и меняют правила (история, счётчики, признаки, прошлые события, связи), и её устройство допускает все сценарии правил (повтор, отмена, сброс, несколько событий за период);
   - событие, которое запускает действие или меняет состояние: определено ли, что считается этим событием (повтор того же значения, выключение и повторное включение, изменение без фактической разницы).
2. **Перечень недостающего:** находка о неполноте перечисляет всё недостающее в этом месте (условия, ветки, поля, ответы, ошибки, нефункциональные характеристики), а не первый пример.

**Откуда направления.** Сравнили по дефектам эталона, что базовая линия находит, а агент пропускает или находит частично (5 прогонов агента: 3 B контрольной точки и 2 с чек-листами #35). Пропуски агента сгруппировались в четыре вида: ветки схемы процесса, модель данных против правил, определение события-триггера и неполный перечень недостающего в одной находке. Формулировки в промпте общие: ни одного слова, имени, числа или примера из документа и эталона, `tests/test_prompt_leak.py` зелёный. Риск подгонки есть, потому что направления выбраны по пропускам на этом же документе. Поэтому ниже отдельно показано, сколько прироста дали дефекты, которые смотрели, а сколько остальные, и прогон на чужом документе.

## Откуда прирост

Средняя доля прогонов, где дефект найден (found или partial), правка против пяти прогонов без неё:

- **Остальные дефекты** (не смотрели): +1,1 дефекта на прогон (#33, #35, #37, #39, #40). Это рост полноты, который не объясняется подгонкой.

## Precision (разметка моделями вслепую, #49)

Opus 5.5 и Fable 5.2 (`high`) независимо разметили 201 находку четырёх прогонов вперемешку, не зная, кто их писал; контрольных ложных находок поймано 27 из 29 и 28 из 29. Результат: [`2026-11-26-precision-recall-v2.md`](2026-11-26-precision-recall-v2.md).

| Прогон | Находок | Оба разметчика: строгая / мягкая |
|---|---:|---|
| Правка, прогон 1 | 55 | 38,2 % / 92,7 % |
| Правка, прогон 2 | 52 | 38,5 % / 84,6 % |
| Как в main (с чек-листами), прогон 1 | 51 | 33,3 % / 90,2 % |
| Один промпт (A), прогон 1 | 43 | 53,5 % / 97,7 % |

Строгая precision не упала (38 % против 33 %), мягкая в пределах разброса между прогонами. Шум по судье 1,9 % (одна находка на прогон). Рост recall не куплен ценой precision. Отставание от одного промпта по строгой precision остаётся: агент чаще пишет мелкие находки, которые разметчики считают «спорно».

## Чужой документ: ТЗ кейса (docs/case/task.md)

Эталона нет. С правкой 31 находка против 24 без неё (`evals/results/recall/task-v2/run-1`, проход 135 с и $0,38, весь прогон 399 с и $1,31). Новые находки по делу: неясно, какая дата в паспорте прогона; «критичный дефект» задан только примерами; расположение отчёта задаётся двумя способами; отчёт и исполнитель названы по-разному в нескольких местах; дублирование положений. Явно шумных новых находок при просмотре нет (precision не размечали).

## Эффорт

Профиль `submit` (Opus `xhigh`) без правки промпта дал 84,4 % (1 прогон) при вдвое большем ответе (50 тыс. токенов) и цене прохода $1,11. Больше рассуждения не прибавило полноты: на этом документе её прибавляет то, что модель просят проверить, а не глубина. Один прогон, поэтому это наблюдение, а не вывод; профиль `submit` с правкой не мерили.

## Решение

Правка остаётся в промпте поиска по умолчанию: recall одного прохода 94,4 % против 86,7 % у main и 93,3 % у одного промпта, критичные 100 % строго, шум и precision не хуже. Цена: проход поиска дороже примерно на 20 % ($0,81 против $0,68) и дольше на 35 с.

## Как повторить

Прогоны шли отдельными папками со своим кешем (нарезка из кеша прогона `checklists/cl/run-1`, остальное живое):

```bash
cd evals/results/recall/v2/run-1 && uv run --project ../../../../.. validator ../../../../../data/input/requirements.md report.md --backend cli --profile quick --passes 1
uv run python -m evals.eval evals/results/recall/v2/run-1 evals/results/recall/v2/run-2 --name recall-v2
uv run python -m evals.precision label evals/results/recall/v2/run-1 evals/results/recall/v2/run-2 evals/results/checklists/cl/run-1 evals/results/baseline/run-1 --name recall-v2
```

Прогон `xhigh` то же с `--profile submit` на коде без правки. Вердикты судьи и разметчиков в `evals/cache/`: повтор eval без сети `--judge cache` и `--mode cache`.
