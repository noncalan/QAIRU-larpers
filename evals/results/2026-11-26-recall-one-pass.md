# Полнота одного прохода: правка промпта поиска

26.11.2026, Астана. Задача от Нурдаулета: поднять полноту одного прохода (recall по эталону) хотя бы до уровня одного промпта (базовая линия A, 93,3 %), честно и без подгонки под эталон. Протокол как на контрольной точке #37: агент, 1 проход Opus 5.5 `medium`, вход `data/input/requirements.md`, судья исследования 21 (Opus 5.5 `high`, вслепую), precision разметкой двумя моделями вслепую (#49).

## Что поменяли (версия v3, по умолчанию)

Два добавления в `src/validator/prompts/search_system.md`, остальное как было.

1. **Новый шаг 7 «Сверь представления одного поведения между собой»** (общие приёмы тест-дизайна):
   - схема процесса (BPMN, блок-схема, диаграмма состояний или последовательности): у каждого условия из текста есть ветка, у каждой развилки описаны все исходы, порядок шагов и участники совпадают с текстом;
   - модель данных: в ней есть, где хранить всё, что читают и меняют правила, и её устройство допускает все сценарии из шага 4 (граничные значения, периоды, переходы состояний, повтор и отмена событий и т. д., шаг 4 был в промпте и раньше);
   - событие, которое запускает действие или меняет состояние: однозначно ли определено, что считается этим событием и что нет, и что происходит в его граничных случаях.
2. **Перечень недостающего:** находка о неполноте перечисляет всё недостающее в этом месте (условия, ветки, поля, ответы, ошибки, нефункциональные характеристики), а не первый пример.

**Откуда направления.** Сравнили по дефектам эталона, что базовая линия находит, а агент пропускает или находит частично (5 прогонов агента: 3 B контрольной точки и 2 с чек-листами #35). Пропуски сгруппировались в четыре вида: ветки схемы процесса, модель данных против правил, определение события-триггера, неполный перечень недостающего в одной находке. Формулировки в промпте общие: ни одного слова, имени или числа из документа и эталона, `tests/test_prompt_leak.py` зелёный.

**История: версия v2 снята на ревью.** В первой версии шага 7 (v2) были примеры в скобках: для события «повтор того же значения, выключение и повторное включение, изменение без фактической разницы», для модели данных «история, счётчики, признаки, прошлые события, связи между записями» и «повтор, отмену, сброс, несколько событий за период». Ревью (интегратор, PR #111) нашло, что они слишком близки к дефектам эталона #43 и #38 (и #16), то есть это смысловая подгонка (CLAUDE.md, правило 2). Примеры убрали, вместо них общие слова и ссылка на шаг 4. Цифры v2 оставлены ниже как история: [`2026-11-26-recall-v2.md`](2026-11-26-recall-v2.md).

## Precision (разметка моделями вслепую, #49)

Opus 5.5 и Fable 5.2 (`high`) независимо разметили 99 находок двух прогонов v3, не зная, кто их писал; контрольные ложные находки пойманы все (15 из 15 у каждого). Результат: [`2026-11-26-precision-recall-v3.md`](2026-11-26-precision-recall-v3.md).

| Прогон | Находок | Оба разметчика: строгая / мягкая | Opus 5.5 | Fable 5.2 |
|---|---:|---|---|---|
| v3, прогон 1 | 49 | 36,7 % / 95,9 % | 44,9 % / 95,9 % | 53,1 % / 100 % |
| v3, прогон 2 | 50 | 48,0 % / 96,0 % | 54,0 % / 96,0 % | 56,0 % / 96,0 % |

Рост recall не куплен ценой precision: шум по судье 0 %, «ложными» разметчики признали 4 % находок. Оговорка: в этой разметке не было находок базовой линии вперемешку, пачки собраны иначе, поэтому сравнение с прошлыми разметками ниже примерное.

Для сравнения из прошлых разметок той же командой: main с чек-листами (cl/run-1) 33,3 % / 90,2 %, v2 38,2–38,5 % / 84,6–92,7 %, один промпт (baseline/run-1) 53,5 % / 97,7 % (оба разметчика, строгая / мягкая, [`2026-11-26-precision-recall-v2.md`](2026-11-26-precision-recall-v2.md)).

## Чужой документ: ТЗ кейса (docs/case/task.md)

Эталона нет. Прогон версии v2 (не v3): 31 находка против 24 без правки (`evals/results/recall/task-v2/run-1`, проход 135 с и $0,38). Новые находки по делу: неясно, какая дата в паспорте прогона; «критичный дефект» задан только примерами; расположение отчёта задаётся двумя способами; отчёт и исполнитель названы по-разному. Явно шумных новых находок при просмотре нет. В ТЗ кейса нет схем процессов и модели данных, поэтому снятые примеры v2 на этот прогон почти не влияли; v3 на нём отдельно не гоняли.

## Эффорт

Профиль `submit` (Opus `xhigh`) без правки промпта дал 84,4 % (1 прогон, [`2026-11-26-recall-xhigh-base.md`](2026-11-26-recall-xhigh-base.md)) при вдвое большем ответе (50 тыс. токенов) и цене прохода $1,11. Больше рассуждения не прибавило полноты: её прибавляет то, что модель просят проверить. Один прогон, поэтому это наблюдение, а не вывод; профиль `submit` с правкой не мерили.

## Решение

v3 по умолчанию в промпте поиска: recall одного прохода 97,8 % (2 прогона) против 86,7 % у main и 93,3 % у одного промпта, критичные 100 % строго, шум 0 %. Цена: проход поиска дороже примерно на 15 % ($0,79 против $0,68) и дольше на 25 с.

## Как повторить

Прогоны шли отдельными папками со своим кешем (нарезка из кеша прогона `checklists/cl/run-1`, остальное живое):

```bash
cd evals/results/recall/v3/run-1 && uv run --project ../../../../.. validator ../../../../../data/input/requirements.md report.md --backend cli --profile quick --passes 1
uv run python -m evals.eval evals/results/recall/v3/run-1 evals/results/recall/v3/run-2 --name recall-v3
uv run python -m evals.precision label evals/results/recall/v3/run-1 evals/results/recall/v3/run-2 --name recall-v3
```

Вердикты судьи и разметчиков в `evals/cache/`: повтор eval без сети `--judge cache` и `--mode cache`.
