# Ревью требований: «Уведомление о расходах по карте»

**Критерии проверки:**
- ISO/IEC/IEEE 29148:2018, п. 5.2.5 (свойства отдельного требования): необходимость, уместность, однозначность, полнота, единичность (singular), реализуемость, проверяемость, корректность, соответствие стандарту.
- ISO/IEC/IEEE 29148:2018, п. 5.2.6 (свойства набора требований): полнота, согласованность, реализуемость, понятность, валидируемость.
- IEEE 830-1998, п. 4.3: корректность, однозначность, полнота, согласованность, ранжированность, проверяемость, модифицируемость, трассируемость.

**Шкала критичности:**
- 🔴 **Критический** — противоречие или пробел, из-за которого разные участники реализуют или протестируют функцию по-разному. Есть риск ошибки в продуктиве.
- 🟠 **Высокий** — без уточнения не удастся завершить реализацию или тестирование.
- 🟡 **Средний** — неоднозначность или неполнота, которую можно закрыть вопросом к аналитику.
- 🟢 **Низкий** — оформление, терминология, шаблон.

## Часть A. Новый функционал

### A.1. Цели, архитектура, UI, BPMN

| № | Цитата | Нарушенное свойство | Почему | Критичность |
|---|---|---|---|---|
| A-01 | «узнать о достижении личного бюджета **в момент покупки**» | Согласованность (29148 5.2.6; 830 4.3.4), однозначность | НФТ разрешает «в течение минуты после получения события», а событие приходит только после проведения покупки. Слова «в момент покупки» противоречат НФТ и непроверяемы. Термин «личный бюджет» больше нигде не используется, в остальном тексте он называется «порог». | 🟡 |
| A-02 | «Карточный процессинг → **учёт расходов** → сервис push» / «Процессинг → **сервис расходов**» / «AlertsController → **хранилище настроек**» при «Мобильное приложение → **сервис настроек**» | Понятность (29148 5.2.6), однозначность (830 4.3.2) | Один компонент назван по-разному. Нельзя понять, это одна система или разные. Глоссария нет. | 🟢 |
| A-03 | «На экране видны переключатель, поле «Порог, ₸», **сумма за месяц** и кнопка «Сохранить»» | Полнота (29148 5.2.5), однозначность | Не определено, за какой месяц показывается сумма (текущий по Алматы?) и учитываются ли возвраты. Не указан источник данных: в API (часть B) нет метода, который возвращает накопленную сумму. Не описаны начальное состояние экрана и поведение после успешного сохранения. | 🟠 |
| A-04 | «При ошибке ввода сообщение появляется под полем» | Полнота, проверяемость (830 4.3.6) | Не перечислены случаи ошибки (пусто, дробное число, вне диапазона, нечисловой ввод). Не задан текст сообщения. Неясно, валидация выполняется на клиенте или по ответу API (там текст «Проверьте сумму»). Не описаны ошибки 401/403/404/500. | 🟡 |
| A-05 | «Проведение покупки → пересчёт расходов → проверка порога → при достижении отправка push → завершение» | Полнота (29148 5.2.6), согласованность | В схеме нет проверки признака «включено», ограничения «один push в месяц», обработки возврата, переводов и снятий, повторной доставки события. Процесс настройки порога клиентом тоже не отражён. Чек-лист требует «схему полного бизнес-процесса», схема его не покрывает. | 🟡 |

### A.2. Функциональные требования

| № | Цитата | Нарушенное свойство | Почему | Критичность |
|---|---|---|---|---|
| A-06 | **Ф-3** «На карту приходится **максимум один** такой push за календарный месяц» vs **Ф-4** «следующее достижение вызывает push **независимо от истории предыдущей настройки**» | Согласованность (29148 5.2.6; 830 4.3.4) | Пример: в этом месяце push уже был, клиент поднял порог выше накопленной суммы, затем сумма снова его достигла. По Ф-4 push нужен, по Ф-3 он запрещён. Без решения разработчик и тестировщик выберут разное поведение. | 🔴 |
| A-07 | **Ф-2** «Месяц определяется по **дате совершения** покупки» vs критерий приёмки «Покупка **31 января в 23:58** … Провести 1 февраля в 00:03 по Алматы → **Февральский** счётчик вырос» | Согласованность, корректность (830 4.3.1) | По Ф-2 покупка, совершённая 31 января, относится к январю. Критерий относит её к февралю, то есть использует дату проведения. Если 23:58 указано не по Алматы, критерий неоднозначен, потому что часовой пояс не указан. Так или иначе, эталон приёмки противоречит требованию. | 🔴 |
| A-08 | **Ф-2** «по дате совершения покупки **в Алматы**» | Однозначность (830 4.3.2) | Город не является часовым поясом. Нужно указать явно, например UTC+5 (с 01.03.2024 Казахстан перешёл на единый UTC+5). Также не указано, откуда берётся дата: время авторизации, транзакции или локальное время терминала. | 🟠 |
| A-09 | **Ф-2** «В расходы входят **проведённые** покупки» | Однозначность, полнота | Термин «проведённые» не определён: авторизация (холд) или клиринг/списание. Нет правил для отмены авторизации, покупок в иностранной валюте (какая сумма в KZT учитывается) и покупок, совершённых в одном месяце, а проведённых в другом. Неясно, отправляется ли push за прошедший месяц. | 🔴 |
| A-10 | **Ф-2** «Переводы и снятие наличных исключаются» | Полнота (29148 5.2.5) | Других типов операций классификация не покрывает: оплата услуг, комиссии, quasi-cash, пополнения, P2P через эквайринг, рекуррентные платежи. Нужен закрытый перечень учитываемых типов (по MCC или по коду операции). | 🟠 |
| A-11 | **Ф-2** «Возврат уменьшает расходы месяца **исходной покупки**» | Полнота, реализуемость (29148 5.2.5) | Не описано, как возврат связывается с исходной покупкой (по какому идентификатору). Нет правил для возврата без связи, частичного возврата, возврата, который пришёл раньше покупки, и отрицательного итога. Неясно, влияет ли возврат в прошлый месяц на push, уже отправленный в прошлом месяце. | 🟠 |
| A-12 | **Ф-2** (4 правила в одном пункте), **Ф-1** (диапазон + значение по умолчанию), **Ф-3** (условие + лимит) | Единичность (29148 5.2.5 singular), модифицируемость (830 4.3.7) | Несколько требований объединены под одним идентификатором. Их нельзя по отдельности трассировать к тестам и менять. | 🟢 |
| A-13 | **Ф-1** «Держатель **активной** карты **KZT** задаёт…» | Полнота | Не описано поведение для неактивной карты, карты в другой валюте и карты, которая стала неактивной при включённом уведомлении. В API нет проверок активности и валюты, нет кодов ошибок для этих случаев (см. B-12). | 🟠 |
| A-14 | **Ф-1** «По умолчанию уведомление выключено» | Полнота | Не задано значение порога по умолчанию. API требует `amount` как обязательный параметр, поэтому неясно, что показывать в поле и что отправлять, если клиент только переключает тумблер. | 🟡 |
| A-15 | **Ф-3** «клиент **получает** push» | Проверяемость (830 4.3.6), уместность | Доставку на устройство система не контролирует: push может быть отключён в ОС или устройство офлайн. Проверяемая формулировка: «система передаёт в сервис push». Так же сформулировано в НФТ. | 🟡 |
| A-16 | **Ф-3** «Когда расходы переходят от суммы ниже порога к сумме, равной порогу или выше…» | Полнота, согласованность с Ф-1 | Нет условия «уведомление включено». Не описан случай, когда порог пересечён при выключенном уведомлении, а затем клиент его включил. «Календарный месяц» не привязан к часовому поясу из Ф-2. | 🟠 |
| A-17 | **Ф-4** «**Если она ниже нового порога**, следующее достижение вызывает push» | Полнота (29148 5.2.5) | Нет ветки «накопленная сумма ≥ нового порога»: отправить push сразу, не отправлять до конца месяца или отправить при следующей покупке? Не описано, как на признак отправки влияет выключение и повторное включение уведомления. | 🟠 |

## Часть B. REST API

| № | Цитата | Нарушенное свойство | Почему | Критичность |
|---|---|---|---|---|
| B-01 | «Description: **Сохранение** порога. Функциональные требования: **чтение** порога» | Согласованность, однозначность | Назначение метода противоречит само себе. | 🟠 |
| B-02 | «REST type: **GET**», URL `/alerts/saveLimit`, `curl -G … --data` | Корректность, уместность (29148 5.2.5) | GET по RFC 9110 должен быть безопасным и не менять состояние. Изменяющий запрос через GET кэшируется, повторяется прокси и попадает в логи вместе с параметрами. Нужен PUT/POST. Глагол в URL противоречит REST-стилю. | 🔴 |
| B-03 | «Request URL: Dev: `/alerts/saveLimit`. Prod: **—**», «Swagger: **—**» | Полнота | Нет боевого адреса и спецификации контракта. | 🟡 |
| B-04 | «Content-Type: `application/json`. **Тело не используется**» | Согласованность | Content-Type указан для отсутствующего тела. | 🟢 |
| B-05 | Шаг 5 «При отклонении суммы вернуть **прежнее состояние** и результат ERROR» vs пример ERROR `{"result":"ERROR","message":"Проверьте сумму"}` vs таблица `amount` — «**При успехе**» | Согласованность | Логика требует вернуть прежнее состояние, но пример и таблица ответа его не содержат. | 🟠 |
| B-06 | Ошибка суммы возвращается в «**200** … `"result":"ERROR"`» vs «**400.** … если параметры запроса заполнены неверно» | Согласованность, однозначность | Для недопустимой суммы не определено, отдавать 200+ERROR или 400. То же для `enabled=2`, дробного `amount`, пустого `cardId`. Клиент не сможет корректно обработать ответ. | 🔴 |
| B-07 | «Если результат 200 **или 201** — успешный» / заголовок «200. Successful — **Created**» | Согласованность, корректность | Код 201 нигде не описан. «Created» — это текст статуса 201, а не 200. | 🟡 |
| B-08 | «Если результат 400, 401 **и далее** — неуспешный» | Однозначность | Перечень кодов открыт и не совпадает со списком статусов (там нет 404, а 403 фактически не используется). | 🟢 |
| B-09 | «**403.** … доступ запрещен» → «Для чужой карты возвращается **404**» | Согласованность | В разделе 403 описан 404. Неясно, бывает ли 403 вообще. Код 404 отсутствует в общем перечне статусов. | 🟠 |
| B-10 | Ответ: `result` — «OK / ERROR» (без условия) vs примеры 400/401/404/500 только с `message` | Согласованность | Схема ответа разная для разных кодов и не совпадает с таблицей. | 🟡 |
| B-11 | Запрос `amount` / `enabled` — **integer**; ответ `amount` / `enabled` — **string** | Согласованность | Один и тот же параметр имеет разные типы в запросе и ответе. | 🟡 |
| B-12 | Логика: «1. Проверить сессию. 2. Проверить принадлежность карты. 3. Проверить сумму и переключатель» | Полнота, согласованность с Ф-1 | Нет проверки, что карта активна и в KZT (Ф-1). Нет кодов и текстов ошибок для этих случаев. | 🟠 |
| B-13 | `cardId` — string, 1–64, «Карта клиента» | Однозначность, безопасность | Формат не определён: токен, внутренний ID или PAN. Если это PAN, он передаётся в query-строке GET и оседает в логах (нарушение PCI DSS). | 🟠 |
| B-14 | Особые правила: «3. Изменение порога сохраняет накопленные расходы» | Уместность, модифицируемость (830 4.3.7: без избыточности) | Метод работает только с хранилищем настроек, накопление ведёт сервис расходов. Правило дублирует Ф-4 и не реализуется этим методом. При изменении Ф-4 появится расхождение. | 🟢 |
| B-15 | «1. Целое число тенге, обе границы включены» | Однозначность | Границы в правиле не названы, они есть только в таблице параметров. Тоже дублирование. | 🟢 |
| B-16 | `enabled` Mandatory «Да» и `amount` Mandatory «Да» | Полнота, согласованность с UI | Не описано, обязателен ли `amount` при `enabled=0` и что делать, если порог ещё не задан (см. A-14). | 🟡 |
| B-17 | Документ в целом | Полнота (29148 5.2.6) | Нет метода чтения настроек и суммы за месяц, который требуют раздел интеграции и UI (см. A-23). | 🔴 |
