# Чужие документы: результаты (#48)

Прогоны агента на документах, которые писали не мы и на которых агента не настраивали ([`data/holdout/README.md`](../../data/holdout/README.md): источники, лицензии, SHA-256). Эталона дефектов у них нет, поэтому полноту (recall) не считаем. Меряем долю сверенных цитат и precision по слепой разметке двумя моделями (#49), а для ТЗ кейса ещё и совпадение вопросов агента с вопросами участников kick-off.

**Состояние на ночь 26.11.2026.** Два документа (`c4` и ТЗ кейса) измерены полностью: прогон агента, разметка двумя разметчиками (Opus 5.5 и Fable 5.2), сравнение вопросов с kick-off двумя судьями. Ещё два документа (`finuchet`, чужой PDF на 18 страниц, и `repair-webapp`) лежат в `data/holdout/`, но прогонов на них пока нет: раздел «Что осталось».

Промпты, код и правила агента по этим результатам не правились ([`docs/no-overfitting.md`](../../docs/no-overfitting.md)). Все числа ниже собраны кодом в [`summary.md`](summary.md) (`uv run python -m evals.holdout_summary`), тест `tests/test_eval_holdout.py` сверяет этот файл с пересчётом.

Как читать столбцы precision. Строгая: разметчик сказал «настоящий» (дефект мешает разработке или тестированию). Мягкая: «настоящий» или «спорно». «Оба»: строгая, если «настоящий» сказали оба разметчика, мягкая, если ни один не сказал «ложный». Это разметка моделями, не людьми.

Откуда цифры:

- **Требований, находок, нарушений, вопросов:** `report.json` прогона ([`c4/report.json`](c4/report.json), [`task/report.json`](task/report.json)): `segmentation.requirements`, `verification.findings`, находки с `verdict: violation`, `questions`. По согласию двух разметчиков: на c4 18 настоящих, 15 спорных, 1 ложная из 34; на ТЗ кейса 5 настоящих, 20 спорных, 7 ложных из 32. ### Можно ли верить разметчикам

В каждую пачку код подмешал 5 заведомо ложных контрольных находок. Оба разметчика пометили «ложный» все 5 из 5 на обоих документах. Оговорки:

- Пачка на документ одна, поэтому все контрольные одного вида, «придирка без влияния на тест»; контрольных с подменённой цитатой нет ([`evals/README.md`](../README.md), раздел «Precision (#49)»).
- Находки писал Opus 5.5, и первый разметчик та же модель. Второй разметчик, Fable 5.2, другая модель: на c4 он строже (52,9 % против 61,8 %), на ТЗ кейса чуть мягче (31,2 % против 28,1 %).
- На c4 разметчики согласны в 91,2 % находок (κ 0,83). На ТЗ кейса только в 62,5 % (κ 0,38): там много находок, где граница между «настоящий» и «спорно» зависит от вкуса, поэтому строгая цифра «оба» (15,6 %) заметно ниже цифры каждого разметчика.

### Как читать цифры

- **c4 не хуже документа кейса.** На `requirements.md` та же разметка дала по согласию двух разметчиков 42,4 % / 96,0 % на 99 находках двух прогонов ([`evals/results/2026-11-26-precision-recall-v3.md`](../results/2026-11-26-precision-recall-v3.md), версия агента раньше текущей). На c4 вышло 52,9 % / 97,1 %: на чужом API-документе агент не стал шумнее. Все 7 критичных находок c4 оба разметчика назвали настоящими.
- **На ТЗ кейса находки слабее.** По согласию двух разметчиков настоящих 5 из 32 (15,6 %), ложных 7 (21,9 %). Из 3 критичных одна настоящая у обоих и две спорные. Из 12 незначительных ни одной настоящей у обоих. ТЗ кейса это короткое задание на хакатон, а не спецификация продукта: многие находки про порядок оценки и сдачи разметчики назвали пожеланиями. Это наблюдение, а не повод править промпт: правки по холдауту запрещены, кандидаты в правки перечислены в файле precision, раздел «Ложные по мнению всех разметчиков».
- **Вывод без прикрас.** На документе того же жанра, что документ кейса (требования к API и данным), качество находок держится. На документе другого жанра (условия конкурса) каждая пятая находка лишняя, а «незначительные» находки почти все спорные или ложные. Критичные находки остаются надёжными: из 10 критичных на двух документах ни одной ложной.
- Один прогон на документ, поэтому стабильность здесь не видна.

## Вопросы агента и вопросы участников kick-off

На kick-off участники задали организаторам 13 вопросов по содержанию ТЗ ([`kickoff_questions.md`](kickoff_questions.md), список выписан до того, как мы увидели вопросы агента). Агент к тому же ТЗ задал 15 вопросов. Два судьи, Opus 5.5 и Fable 5.2, независимо сопоставили два списка ([`kickoff.md`](kickoff.md)).

| Судья | «Совпало» | «Частично» | «Нет» | Строгая / мягкая доля |
|---|---:|---:|---:|---:|
| Opus 5.5 | 1 | 6 | 6 | 7,7 % / 53,8 % |
| Fable 5.2 | 1 | 5 | 7 | 7,7 % / 46,2 % |
| Оба | 1 | 5 | 7 | 7,7 % / 46,2 % |

Согласие судей 92,3 % (κ 0,87). Как это читать:

- **Точно совпал один вопрос из 13**: в каком формате должен быть отчёт (K-05 и вопрос агента Q-13). Ещё пять вопросов участников агент задел частично: ограничения по модели и чей ключ (Q-12), формат входа (Q-01), какие критерии стандартов обязательны (Q-03).
- **Семь вопросов участников агент не задал вовсе.** Почти все они про то, как делать решение и как его будут оценивать: можно ли брать готовый harness, нужен ли интерфейс, сколько агентов, какая структура репозитория, один документ или любой. Агент ищет неясности в тексте требований и таких вопросов не задаёт. Это ограничение, а не достоинство: вопросы «что останется за рамками текста» живые люди задали, агент нет.
- **В обратную сторону:** из 15 вопросов агента оба судьи связали с вопросами участников только 4. Остальные 11 участники не задавали. Насколько эти 11 полезны, этот замер не говорит.
- Цифра маленькая, и мы её не округляем в свою пользу: для критерия «Уточнение» честно говорить «агент задаёт вопросы по тексту ТЗ, один из них совпал с вопросом участников дословно, пять частично».

## Как шёл прогон

| Документ | Версия агента | Профиль | Вызовов модели | Время | Цена по тарифу API | Код возврата |
|---|---|---|---:|---:|---:|---:|
| `c4` | `e8ef344` (main, чистое дерево) | `standard`, 1 проход, `--backend cli`, `--max-budget-usd 5` | 8, сбоев 0 | 8,4 мин | $1,62 | 0 |
| `task` | `e8ef344` (main, чистое дерево) | то же | 8, сбоев 0 | 8,6 мин | $1,58 | 0 |

Источник: `passport` и `metrics` в `report.json` (`agent_version`, `agent_dirty: false`, `calls_total`, `calls_cached: 0`, `duration_s`, `cost_usd`). Все ответы модели живые, из кеша ни одного. Платили лимитом подписки, цена показана по тарифу API для сравнения. Сырые ответы модели лежат в `run/` каждого документа: по ним прогон повторяется без сети (`--backend replay --replay evals/holdout/<документ>/run`).

Разметка и судьи: разметка c4 стоила $0,66, разметка ТЗ кейса $0,71, судьи kick-off $0,42 (по тарифу API, оба разметчика вместе; из файлов precision и `kickoff.json`).

Команды:

```bash
uv run validator data/holdout/c4/c4_tech_task.md evals/holdout/c4/report.md --backend cli --profile standard --max-budget-usd 5
uv run validator data/holdout/task/task.md evals/holdout/task/report.md --backend cli --profile standard --max-budget-usd 5
uv run python -m evals.precision label evals/holdout/c4 --document data/holdout/c4/c4_tech_task.md \
  --name holdout-c4 --out-dir evals/holdout/c4
uv run python -m evals.precision label evals/holdout/task --document data/holdout/task/task.md \
  --name holdout-task --out-dir evals/holdout/task
uv run python -m evals.kickoff
uv run python -m evals.holdout_summary
```

Пересчёт без сети: к командам `evals.precision` и `evals.kickoff` добавить `--mode cache` (ответы разметчиков и судей лежат в `evals/cache/`).

## Примеры находок для README и слайдов

Первые две находки оба разметчика пометили «настоящий». Третью Opus 5.5 назвал настоящей, а Fable 5.2 спорной. Цитаты сверены с документом кодом и вручную.

1. **ТЗ кейса: формат входа противоречит выданному документу** (`task`, F-02, критично, [`task/report.md`](task/report.md)). Строка 13: «Проверяемый документ выдают организаторы отдельно» (дальше в скобках ссылка на `docs/requirements.md`), а строка 29: «Запускает агента и передаёт этот документ на вход (PDF + при поддержке других форматов)». Выдан Markdown, а обязательным назван PDF: команда может сделать поддержку не того формата. На kick-off это место споткнуло и самих организаторов: «Кстати, Аскар, я не помню мы в ПДФ формате в итоге рекверментсот дали или в МД» ([`docs/case/kickoff-transcript.md`](../../docs/case/kickoff-transcript.md), 14:13).
2. **c4: кратность связи «сотрудник — компания» противоречит удалению** (`c4`, F-02, критично, [`c4/report.md`](c4/report.md)). Строка 27: «Привязка сотрудника к компании (1:1 или null).», строка 63: «Удалить компанию (если нет сотрудников).» Если связь 1:1, у компании не бывает «сотрудников» во множественном числе; от ответа зависят схема БД (уникален ли внешний ключ) и тест привязки второго сотрудника.
3. **c4: длина ИНН в тексте и в схеме OpenAPI расходится** (`c4`, F-16, важно). Строка 38: «`inn` (уникальный, 10/12 цифр)», а строка 111: «minLength = 10, maxLength = 12». Схема пропускает 11 цифр, которых по тексту быть не может: документация API будет описывать не то, что проверяет валидация.
