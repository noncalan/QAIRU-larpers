# Eval: эталон, судья, метрики

Issue #24. Считает, насколько полно агент (и базовая линия «один промпт») находит дефекты эталона `docs/gold/defects.md`, насколько честны цитаты и насколько стабилен результат между прогонами. Протокол и правило D-011: `docs/plan.md`, раздел «Протокол eval и правило D-011».

**Эталон не утекает в агента** (CLAUDE.md, правило 2). Эталон читает только этот пакет. Код агента в `src/validator` не импортирует `evals` и не ссылается на файлы эталона, а в его файлах нет ни одной последовательности из 6 слов описаний дефектов: это проверяет `tests/test_gold_isolation.py`. Результаты eval показывают только номер дефекта, важность и критерий, без текста дефекта, поэтому их можно смотреть при работе над промптами.

## Запуск

```bash
# прогоны одной конфигурации (по умолчанию: кеш вердиктов, при промахе живой судья)
uv run python -m evals.eval out/run-1 out/run-2 out/run-3 --name agent-1pass

# только кеш, без сети (промах = ошибка)
uv run python -m evals.eval evals/results/baseline/run-1 --name baseline --judge cache

# smoke без сети: прогон агента на бэкенде fake получает судью-фикстуру
uv run validator data/input/requirements.md out/report.md --backend fake
uv run python -m evals.eval out/ --name smoke
```

Результат: `evals/results/<дата>-<имя>.json` (всё для машин и таблиц) и `.md` (для людей и описания PR). Дата по времени Астаны. Повторный eval с тем же именем в тот же день прошлый результат не затирает: к имени добавляется время (`<дата>-<имя>-<ЧЧММСС>`).

Все папки одного вызова считаются прогонами **одной конфигурации** (например, «агент, 1 проход medium»): по ним считаются средние, объединение, pass^k и Жаккар. Разные конфигурации (A, B, B′, C в протоколе) это разные вызовы с разными `--name`.

| Флаг | Что делает |
|---|---|
| `--judge auto` | по умолчанию: прогону на бэкенде `fake` отвечает судья-фикстура, остальным кеш, при промахе живой вызов |
| `--judge cache` | только кеш `evals/cache/judge/`, без сети |
| `--judge cli` | кеш, при промахе живой вызов `claude -p` (подписка) |
| `--judge fake` | ответы из `--fixtures` (`evals/fixtures/llm/judge/<номер прогона>.json`) |
| `--judge-format uniform` | по умолчанию, по протоколу: одинаковый пронумерованный список для агента и базовой линии |
| `--judge-format research21` | как в исследовании 21: свободный текст базовой линии целиком, судья нумерует находки сам. Только для сверки с прошлыми замерами |
| `--document` | документ эталона для судьи и сверки цитат, по умолчанию `data/input/requirements.md` |
| `--overrides` | ручные поправки, по умолчанию `evals/overrides.yaml` |

**Сколько стоит живой судья.** Один вызов Opus 5.5 `high` на прогон: 3–6 минут, около $0,5–1 по тарифу API (оплачивается лимитом подписки). Вердикт ложится в `evals/cache/judge/<ключ>.json` и коммитится: повторный подсчёт и чужая проверка цифр лимит не тратят. Ключ это хеш модели, effort, системного промпта, полного запроса и схемы (без номера прогона в вызове eval, в отличие от ключа кеша агента), поэтому новый вердикт нужен, только если поменялись документ, эталон или список находок. В файле кеша нет ни документа, ни эталона, только ответ судьи.

## Что считается прогоном

**Агент:** папка, где лежит `report.json` (или `<имя>.json`, который пишет `validator ВХОД ПАПКА/<имя>.md`), и рядом `run/calls.jsonl`. Судят находки **после верификатора** (`verification.findings`).

**Базовая линия:** папка с сырым ответом модели `answer.md` (или `answer.txt`) и логом `calls.jsonl` (в той же папке или в `run/`). Формат `calls.jsonl` тот же, что у агента (`CallRecord`); его пишет `RecordingClient` клиента модели агента. Пример: `tests/fixtures/eval/baseline-run/` (живой ответ Opus 5.5 `medium` на промпт исследования 11, 25.11.2026).

## Судья

Промпт, схема, модель и effort из `experiments/21-model-effort/run_matrix.py` дословно (`evals/judge.py`), полным именем `claude-opus-5-5`, effort `high`. Судья получает три блока: документ, эталон (`docs/gold/defects.md` целиком, как в исследовании 21) и находки. `tests/test_eval_parity.py` проверяет, что запрос судьи совпадает с запросом исследования 21 побайтово, а метрики на одном вердикте совпадают с `score.py`.

**Список находок** одинаков для агента и базовой линии: JSON-массив объектов `id`, `quote`, `property`, `explanation`, как в исследовании 21 для ответов в JSON. Кто автор списка, судья не видит: нет ни источника, ни `F-NN`, ни ID блоков.

- Агент: `quote` это цитаты находки через « … », `property` это свойство стандарта и тип дефекта («Согласованность, противоречие»), `explanation` это пояснение.
- Базовая линия: код режет свободный текст на находки (`evals/freetext.py`, без модели: перенос в JSON через Haiku к базовой линии не применяем). Пробует три разметки и берёт ту, где больше находок с цитатами: строки таблиц со столбцом «Цитата», разделы под заголовками одного уровня, пункты нумерованного списка. Разделы «Итог», «Вывод», «Шкала» и подобные находками не считаются, вложенные пункты списка остаются в своей находке. Если разметку не узнал, режет по абзацам с цитатами и пишет об этом заметку.
- `--judge-format research21`: базовая линия уходит судье свободным текстом, и находки нумерует сам судья, как в исследовании 21. Тогда число находок это наибольший номер судьи, в таблице «Находки вне эталона» нет цитат и отпечатков, а поправки `findings` по отпечатку не применяются (eval пишет предупреждение).

## Метрики

| Метрика | Как считается |
|---|---|
| Recall | доля 45 дефектов эталона со статусом found или partial (как исследование 21) |
| Recall строгий | только found |
| Критичные | то же по 9 дефектам с важностью «Критично» (1, 2, 3, 4, 6, 8, 14, 25, 34) |
| Recall по важности | отдельно по «Критично», «Средне», «Низко» |
| Объединение | дефекты, найденные хотя бы в одном прогоне конфигурации (с частичными и строго) |
| pass^k критичных | доля критичных, найденных во **всех** прогонах: жюри видит один прогон (исследование 08) |
| Находок | длина списка, который видел судья |
| Шум | находки, которые судья счёл noise, от всех находок прогона |
| Лишние настоящие | находки вне эталона, которые судья счёл настоящими дефектами (precision даёт #49, не судья) |
| Цитаты: дословно / сверены | цитаты модели до фильтра, сверенные `locate_quote` агента: точно / точно или нечётко. Агент: счётчики верификатора по всем кандидатам, включая отброшенные. Базовая линия: цитаты из текста по эвристике исследования 11, склейки «…», « / », « \| » режутся на сегменты, вердикт по худшему сегменту |
| Итоговые сверены | цитаты итоговых находок, сверенные заново по документу прогона. У агента должно быть 100 %: иначе верификатор пропустил выдуманную цитату |
| Жаккар дефектов эталона | средний попарный Жаккар множеств найденных дефектов эталона между прогонами |
| Жаккар находок | средний попарный Жаккар множеств «`stable_key` требования + код свойства» между прогонами агента (находка набора без требования: раздел или цитата). Это метрика правила D-011 |
| Время, цена | из `calls.jsonl` (строка на попытку): цена это сумма `cost_usd` по тарифу API за успешные ответы, включая ответы из кеша и replay (так она равна цене живого прогона); время это длительность прогона из паспорта (у базовой линии сумма попыток). Если часть ответов взята из кеша или replay, время не живое, и eval пишет об этом заметку |

Средние по конфигурации это средние по прогонам. Recall судья считает по эталону, который тоже составлял Claude: это оценка полноты, а не precision.

Отличие от `score.py`: если судья не оценил дефект, мы считаем его пропущенным и пишем предупреждение. `score.py` в этом случае засчитывал критичный дефект как найденный.

## Вопросы автору (#41)

Метрики вопросов исследования 17, п. 4.3 считает код (`validator.questions.metrics`, та же функция пишет `metrics.questions` в `report.json` и строки «Вопросы: …» в разделе «Метрики прогона» отчёта). Eval пересчитывает их по `report.json` прогона агента, до и после критика-самоответа, и кладёт в раздел «Вопросы автору: до и после критика» результата `evals.eval`. Судья и эталон для них не нужны, поэтому есть отдельный запуск без сети:

```bash
uv run python -m evals.questions out/run-1 out/run-2 --name critic   # evals/results/<дата>-questions-critic.{json,md}
```

| Метрика | Как считается |
|---|---|
| Вопросов до / после | до: вопросы в отчёте плюс снятые критиком (`questions_withdrawn`); после: вопросы в отчёте |
| Снято самоответом | доля снятых от вопросов до критика. Снимает код: критик дал цитату-ответ, `locate_quote` нашёл её в документе, и это не то самое место, о котором вопрос |
| Со сценарием | доля вопросов, где критик отметил конкретную ситуацию с данными; вопросы без отзыва критика в знаменатель не идут, без критика «—» |
| Закрытые | доля вопросов с 2–4 различающимися вариантами, у каждого непустое «что поменять» |
| Без ошибок формулировки | доля вопросов без ошибок из списка п. 4.4 по отзыву критика |
| Дубли с находками | вопросы, где критик считает правку однозначной: хватило бы находки с правкой |
| Повторы | пары вопросов со сходством формулировки ≥ 85 (`token_sort_ratio`) или с теми же местами документа |
| Приоритеты, адресаты | распределение P0/P1/P2 и адресатов (разброс адресатов) |
| Жаккар мест | средний попарный Жаккар множеств ID блоков, о которых вопросы, между прогонами (цель исследования 17: от 0,7) |

Сценарий и ошибки формулировки отмечает та же модель, что писала вопросы: это оценка, а не независимая разметка.

## Контрольная точка D-011 (#37)

Прогоны и решение по протоколу `docs/plan.md` («Протокол eval и правило D-011»). A (базовая линия) уже посчитана: `results/2026-11-26-baseline.json`.

```bash
evals/checkpoint.sh                      # B ×3, B′ ×2, C ×3 через подписку, не больше трёх одновременно
evals/checkpoint.sh /tmp/dry fake        # проверка команд без сети на фикстурах
uv run python -m evals.eval evals/results/checkpoint/b/run-{1,2,3} --name checkpoint-b
uv run python -m evals.eval evals/results/checkpoint/b-raw/run-{1,2} --name checkpoint-b-raw
uv run python -m evals.eval evals/results/checkpoint/c/run-{1,2,3} --name checkpoint-c
uv run python -m evals.checkpoint --a evals/results/2026-11-26-baseline.json \
  --b evals/results/<дата>-checkpoint-b.json --b-raw evals/results/<дата>-checkpoint-b-raw.json \
  --c evals/results/<дата>-checkpoint-c.json     # → results/<дата>-checkpoint.{json,md}
```

- **Независимые прогоны.** У каждого прогона своя папка и свой кеш ответов (`.cache/` внутри, в git не идёт): общий кеш вернул бы второму прогону ответы первого. Упавший прогон запускают заново той же командой с его именем (`evals/checkpoint.sh evals/results/checkpoint cli c/run-2`), удачные вызовы возьмутся из его кеша.
- **B′** это `--search-input raw`: поиск видит канонический текст документа без ID блоков, блоки находок код находит по цитатам (`validator.search`). Остальные шаги те же.
- **Правило кодом** (`checkpoint.py`): пороги переписаны из плана константами, сравнение «0,10 и больше» с допуском на округление. «Доля сверенных цитат» в п. 1 это цитаты модели до фильтра, сверенные точно или нечётко (`quotes_verified`): у итоговых находок она 100 % по построению. Выбранная конфигурация для п. 3: C, если по п. 1 три прохода, иначе B (или B′, если по п. 2 сырой текст).

## Ручные поправки

`evals/overrides.yaml`: вердикт человека важнее судьи. Поправка видна в результатах (раздел «Поправки») и учитывается во всех метриках.

```yaml
gold:
  - run: evals/results/baseline/run-1   # метка прогона из результатов или шаблон fnmatch (run-*)
    gold: 34                            # номер дефекта эталона
    status: found                       # found | partial | missed
    finding_ids: [12]                   # номера находок в списке судьи
    by: Нурдаулет
    reason: судья не увидел, что находка 12 про клиринг
findings:
  - finding: 3f2a9c1b7e44               # отпечаток из таблицы «Находки вне эталона»
    verdict: noise                      # real | noise
    reason: придирка к оформлению
```

Метка прогона это путь к его папке от корня репозитория (если папка вне репозитория, полный путь), откуда бы ни запускали eval. Отпечаток находки это хеш её цитаты, свойства и пояснения без номера, поэтому поправка переживает перенумерацию. Поправка `findings` без `run` действует во всех прогонах.
