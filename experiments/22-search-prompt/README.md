# Эксперимент 22: промпт и рубрика поиска дефектов (шаг 4)

Issue #14. Промпт прохода поиска: [`src/validator/prompts/search_system.md`](../../src/validator/prompts/search_system.md) (рубрика и формат ответа) и [`search_user.md`](../../src/validator/prompts/search_user.md) (шаблон, документ подставляется вместо `{document}`, ровно одно вхождение).

## Как мерили

- **Проход:** Opus 5.5 (`claude-opus-5-5`), effort `medium`, свободный текст без `--json-schema` (D-010). Вызов `claude -p` с теми же флагами и чистым окружением, что в исследовании 21. Документ `data/input/requirements.md` показан блоками с ID (`render.py`, формат исследования 18, п. 3.2) или сырым Markdown (B′).
- **Судья:** промпт, схема, модель и effort из `experiments/21-model-effort/run_matrix.py` без изменений (Opus 5.5 `high`, вслепую, эталон видит только судья). Нашему судье идёт только раздел «Находки» (без «Обзора документа»), находки перенумерованы подряд с 1. Базовой линии судья, как в исследовании 21, получает весь ответ и нумерует находки сам.
- **Метрики:** recall по 45 дефектам эталона (found или partial), строгий recall (только found), recall по 9 критичным; доля шума = находки, которые судья счёл «noise», от всех находок; доля дословных цитат (`quote_check.locate` из эксперимента 03, сегменты как в `score.py` исследования 21). У нашего формата цитаты берутся из строк «Цитата:», у базовой линии эвристикой исследования 11. Для режима с блоками ещё: ID блоков, которых нет в документе, и доля цитат, которые лежат внутри указанного блока.
- **Бюджет:** 12 живых вызовов поиска Opus `medium` из 12 разрешённых (3 итерации × 2, сырой текст × 2, базовая линия в тот же день × 2, инъекция × 1, проверка итогового промпта после ревью × 1) и столько же вызовов судьи. `xhigh` и Fable не использовались.
- **Чего не делали, чтобы не подгонять под эталон:** эталон в промпт не попадал; между итерациями смотрели только номера пропущенных дефектов и их столбец «Критерий» (`run.py score`), тексты дефектов не открывали. Правки рубрики общие: словарь терминов, таблицы решений, языковые критерии п. 5.2.7. Слова проверяемого документа и правила 3 CLAUDE.md в промптах проверяет `run.py leak` (6 слов подряд из документа и список запрещённых слов): 0 совпадений.

## Откуда пункты рубрики

Чтобы рубрика не была пересказом эталона (CLAUDE.md, правила 2 и 3), у каждого пункта есть источник, не зависящий от нашего документа:

- свойства и их определения: ISO/IEC/IEEE 29148:2018 п. 5.2.5, 5.2.6, 5.2.7 и IEEE 830-1998 п. 4.3, 4.7 в пересказе исследования 01 (раздел 2), без примеров из нашего документа;
- приёмы проигрывания сценариев (граничные значения, классы эквивалентности, переходы состояний, таблицы решений, предусловия тест-кейса): стандартные техники тест-дизайна (ISTQB Foundation), исследование 03, подход 5;
- словарь терминов: IEEE 830-1998 п. 4.3.4.1 (третий вид конфликта: разные термины для одного объекта) и п. 4.3.2;
- проверка интерфейсов: универсальный чек-лист REST (CLAUDE.md, правило 3 разрешает доменные знания в виде общих чек-листов);
- условия измерения для времени: пример проверяемого нефункционального требования из IEEE 830-1998 п. 4.3.6.

После ревью кода (`/code-review high`) из рубрики убраны три уточнения, у которых такого источника нет: «в описании одного компонента задана логика другого» (Appropriate), «заголовок не совпадает с содержанием» (Correct) и «схема и текст называют участников по-разному» (Comprehensible; общий случай покрывает словарь терминов). Это итоговый промпт, его проверочный прогон ниже в таблице итераций.

## Выводы

1. **Recall итогового промпта на уровне базовой линии, строгий recall ниже.** Итерация 3 дала 91,1 % (2 прогона), итоговый промпт после ревью 95,6 % (1 прогон); три прогона почти одинакового промпта вместе дают в среднем 92,6 %. Базовая линия: 93,3 % в тот же день и 92,6 % в исследовании 21. Разница меньше разброса между двумя прогонами одной конфигурации (у базовой линии 86,7 и 100, у итерации 2 80,0 и 95,6). Критичные 9 из 9 во всех прогонах итерации 3 и итогового промпта. Строгий recall ниже на 9–11 п. п. во всех итерациях (около 70 % против 80–83 %): судья чаще ставит «частично». Вероятная причина: наша находка короткая и про одну суть, а в свободном тексте базовой линии вокруг цитаты длинное рассуждение, которое задевает соседние аспекты эталонного дефекта. Это предположение, отдельно не проверяли.
2. **Что дали взамен** (то, чего у базовой линии нет совсем или что слабее):
   - 100 % цитат дословно есть в документе против 72,5 % у базовой линии: верификатору почти нечего отбрасывать;
   - ID блоков у каждой находки, 0 невалидных ID из ~130 за прогон, 91–98 % цитат лежат внутри указанного блока: привязка к требованию `R-NN` получается кодом;
   - вердикт «неясно» (1–4 за прогон) с тем, что спросить у автора, и строка «Тест: мешает …» (34–38 находок за прогон) с недостающим значением: готовые кандидаты для вопросов автору (#20) и попытки теста (#40);
   - формулировка исправления у каждой находки, у половины (26–28 из 47–54) с `[уточнить: …]`;
   - строгий формат: код разбирает все находки всех 10 прогонов нашего промпта (`parse_findings` в `run.py`, 479 находок), сквозная нумерация без сбоев, тип дефекта и вердикт всегда из списка. Пропуски только в строке «Вердикт»: 13 находок из 479 без неё (модель опускает строку, когда в заголовке уже написано «Неясно…»). Этот формат можно разбирать кодом, а перенос в JSON через Haiku (#18) оставить запасным путём;
   - доля шума 3,8–4,3 % (базовая линия 2,2 %), почти все лишние находки судья считает настоящими дефектами, которых нет в эталоне (5–6 за прогон);
   - команда внутри документа не выполняется и записывается находкой (раздел выше).
3. **Цена.** Проход вдвое дороже базовой линии ($0,66–0,72 против $0,35, 227–249 с против 140 с): выход 27–31 тыс. токенов против 13–18 тыс., из них рассуждение 9–13 тыс. Это важно для D-011: три прохода с этим промптом ≈ $2 по тарифу API. Дешевле не стало, потому что каждая находка несёт 9 полей; урезать поля (например, формулировку исправления) можно в задаче про N проходов, если цена станет решающей.
4. **Разметка блоков не мешает, скорее помогает.** На сыром Markdown тот же промпт дал 85,6 % против 91,1 % с блоками (2 прогона против 2). По правилу D-011, п. 2, блоки оставляем; окончательно решает контрольная точка #37 (B против B′ на настоящем `render_for_model`).
5. **Где промпт пропускает.** Все пропуски итерации 3 и итогового промпта средней и низкой важности: полнота (3 дефекта, один пропущен в обоих прогонах итерации 3) и однозначность (3 дефекта), один раз согласованность. Объединение двух проходов итерации 3 закрывает 97,8 % эталона.

## Ограничения

- По 2 прогона на конфигурацию, итоговый промпт после ревью 1 прогон: разброс recall между прогонами до 15 п. п., разницы меньше 5 п. п. в пределах шума. Сырой текст и инъекцию меряли на промпте итерации 3.
- Эталон составлял Claude, судит тоже Claude (Opus 5.5 `high`), поэтому recall скорее завышен; повтор судьи в исследовании 21 совпал в 178 из 180 решений.
- Итерации подбирались по пропускам на этом же документе (по номерам и столбцу «Критерий»). Правки общие, но проверить обобщение нужно на чужих документах (холдаут, контрольная точка #37).
- `render.py` здесь свой порт `preseg.py`; в агенте документ показывает `render_for_model` из каркаса #15. Формат ID и разметки в `search_user.md` описан так, чтобы подойти обоим.
