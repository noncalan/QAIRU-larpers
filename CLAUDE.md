# QAIRU-larpers: AI Requirements Validator

Команда «QAIRU larpers» на отборе **BCC-HUB x MNU AI Agent Challenge 2026**.
Кейс: https://github.com/BCC-HUB/ai-requirements-validator-task (копия ТЗ: @docs/case/task.md).

Делаем CLI-агента, который читает документ требований (PDF обязательно, MD и DOCX желательно), режет его на отдельные требования, проверяет каждое и весь набор по ISO/IEC/IEEE 29148:2018 (п. 5.2.5, 5.2.6) и IEEE 830-1998 (п. 4.3) и пишет отчёт на русском в файл. Сдаём репозиторий и отчёт, который сгенерировал именно этот агент.

## Текущая фаза

**Исследование → выбор идеи → общий план и issues.** Код агента пока НЕ пишем: сначала команда утверждает идею и план, и решение записывается в `docs/decisions.md`. Исключение: эксперименты в `experiments/` (бенчмарки парсеров, пробные вызовы LLM). Они не являются кодом агента.

## Что оценивает жюри

Жюри (лид QA BCC-HUB): архитектура, техническая реализация, точность решения задачи, **измеримая бизнес-ценность**. Отдельно проверят **битые файлы и документы без текста**: агент обязан выдать понятную диагностику в отчёт, а не упасть. Подробности и ответы kick-off: `docs/case/case-analysis.md`.

Обязательные разделы отчёта (из ТЗ): паспорт прогона (документ, дата, модель, версия агента = коммит/тег), таблица нарезки требований, проверка каждого требования, проверка набора, сводка (число требований, нарушений, критичные), итог (можно ли начинать разработку и тестирование, что исправить первым). Каждое нарушение ссылается на конкретное место документа.

## Жёсткие правила

1. **Секреты.** Никогда не коммить `.env`, ключи и токены, даже на минуту: репозиторий станет публичным, история сохранится. Ключи только в `.env` (он в `.gitignore`). Перед коммитом смотри `git diff --staged`.
2. **Эталон не утекает в агента.** `docs/gold/` используется только для eval. Не вставляй эталонные дефекты в промпты, few-shot, правила линтера. Это подгонка, а жюри проверит «любой документ».
3. **Никакого хардкода под документ.** Правила и промпты общие: без «порога», «Ф-1», «тиынов» и т.п. Доменные знания (финтех, REST) оформляем как универсальные чек-листы.
4. **Каждая находка с цитатой.** Агент не пишет общих фраз: цитата из документа обязательна, код проверяет, что она там есть.
5. **Метрики вместо «на глаз».** Любая правка промпта сопровождается прогоном eval и цифрой в описании PR.
6. **Факты с источниками.** В исследованиях у каждой цифры ссылка и дата, непроверенное помечаем «не проверено». Не выдумывать статьи и API.
7. **Работа через ветки и PR.** Ветка на задачу (`research/…`, `feat/…`, `fix/…`), короткий PR, ссылка на issue (`Closes #N`). В `main` напрямую не пушим.
8. **Свои файлы.** Каждый пишет в свои файлы (`docs/research/<тема>.md`), чужие правим через PR или по договорённости.

## Язык

Документация, README, отчёт агента, issues и PR: по-русски. Код, идентификаторы, имена файлов: по-английски. Сообщения коммитов: коротко, можно по-русски.

## Стек (черновик, утвердим после идеи)

Python 3.11+, `uv` для окружения. Модель в рантайме: **Claude**. До 27.11 вызываем её через подписку командой `claude -p` (решение D-008), к сдаче подключаем Claude API (официальный SDK `anthropic`, ключ `ANTHROPIC_API_KEY` в `.env`, решение D-006). Ключа пока нет: не проси его и не пиши код, который без него не запускается (D-007). Выбор провайдера и модели больше не исследуем; материалы про Gemini в `docs/research/` устарели и помечены. Детали после исследования: `docs/research/`.

Команды:
- `uv sync --group experiments` ставит зависимости для экспериментов.
- `uv run python experiments/<скрипт>.py` запускает эксперимент.

## Как работать с субагентами

Claude Code умеет запускать несколько субагентов параллельно. Пользуйся этим для исследования и проверок.

- **Исследование:** одна тема = один субагент `researcher` = один файл в `docs/research/`. Запускай несколько одновременно одним сообщением. Порядок работы описан в скилле `research-sprint`.
- **Проверка фактов:** `fact-checker` перепроверяет ссылки и цифры в готовом файле исследования.
- **Критика идеи:** `idea-critic` атакует идею с позиции жюри; для выбора между вариантами скилл `council`.
- **Планирование:** скилл `blueprint` режет план на задачи размером с PR.
- **Перед PR:** скилл `verification-loop`, команда `/code-review`, `/security-review` (проверка, что ключи не утекли).
- **Eval:** скилл `eval-harness`; гибрид «правила + LLM»: `regex-vs-llm-structured-text`; бюджет вызовов: `cost-aware-llm-pipeline`; независимая перепроверка: `santa-method`; решения: `architecture-decision-records`.
- Не дублируй работу: перед стартом посмотри открытые issues и `docs/research/README.md`, кто что делает.
- Следи за лимитами подписки: на Pro лучше 3–5 субагентов одновременно, на Max можно больше.

## Карта репозитория

- `docs/gold/defects.md`: эталон из 45 дефектов (только для eval, см. правило 2).
- `docs/research/`: результаты исследования, индекс в `README.md`.
- `docs/ideas/`: кандидаты идей и итог обсуждения.
- `docs/decisions.md`: журнал решений.
- `data/input/`: проверяемый документ (`requirements.md`) и его PDF/DOCX-версии для тестов.
- `experiments/`: одноразовые скрипты экспериментов.
- `.claude/`: настройки, агенты и скиллы Claude Code (общие для команды).
